## 1. 项目定位

**一句话概括**：一个混合尺寸（standard cell + macro）全局布局器。输入 BookShelf 格式电路网表，
输出每个可移动单元的坐标，目标是在密度约束下最小化 HPWL 线长。

核心算法链路：

```
BookShelf 解析  →  Kraftwerk2 二次布局（初始解）  →  ePlace 静电场模型 + Nesterov 加速梯度（全局布局）
                                                    →  Abacus 合法化（选做）  →  可视化
```

对应课程任务 2~7：

| 任务 | 内容 | 交付形态 |
| --- | --- | --- |
| 任务 2 | 布局概念与 BookShelf / LEF / DEF 格式理解 | 认知基础，无代码产出 |
| 任务 3 | BookShelf 格式解析 | 解析器 + 统计信息对拍 |
| 任务 4 | 初始布局设计（≥3 种方法并对比分析） | 随机 / 聚类驱动 / 二次解析 + 对比报告 |
| 任务 5 | 全局布局设计 | ePlace 引擎（本项目核心） |
| 任务 6 | 布局结果分析与可视化 | CImg 出图 + GDSII 导出（KLayout 查看） |
| 任务 7 | 布局合法化（选做） | Abacus 标准单元合法化 / 宏单元模拟退火 |

## 2. 产品形态

### 2.1 形态结论：ISPD 风格的 CLI 引擎

这类软件在学界和工业界的成熟形态高度统一——**不是 GUI 应用，而是一个自包含的命令行引擎**。
ePlace、NTUplace3、mPL6、RePlAce、OpenROAD 的 `gpl` 模块全都是这个形态。

核心交互就一行：

```bash
superplace --aux test_data/adaptec1/adaptec1.aux \
           --config configs/default.json \
           --out results/adaptec1/
```

### 2.2 产出：一个结果目录，而非一个结果文件

```
results/adaptec1/
├── adaptec1.gp.pl        # 布局结果，仍是 BookShelf .pl，可被任何工具消费
├── adaptec1.gds          # GDSII，KLayout 直接打开
├── metrics.csv           # 逐迭代 HPWL / overflow τ / λ / γ / α / 梯度范数
├── summary.json          # 最终 HPWL、各阶段耗时、合法性统计
├── plots/
│   ├── init.png, iter_0050.png, ..., final.png
│   └── convergence.gif   # 收敛动画
└── run.log
```

这个形态的价值在于**可脚本化、可复现、可对比**。任务 4 要求"三种方法对比分析"，
在这个形态下就是换个 `--init-method` 参数跑三次，再把三份 `summary.json` 拼成表格，
而不是手工记录数据。

### 2.3 最终交付物：三个二进制 + 一个库

| 交付物 | 说明 |
| --- | --- |
| `libsuperplace` | 静态库，承载全部逻辑。测试、CLI、GUI 都链接它 |
| `superplace` | CLI 前端，很薄的一层，只负责参数解析与阶段编排 |
| `superplace-check` | 独立的合法性检查器，**不复用布局器的几何代码** |
| `superplace-gui` | （可选）交互式查看器，与 CLI 平级的第二前端 |

拆成"库 + 前端"不是过度设计，而是因为单元测试、批量实验脚本、未来的 GUI
都需要直接链接逻辑层，不能只能通过进程调用。

## 3. 整体架构

### 3.1 四层结构

```
┌─ 编排层  main / Pipeline / Config ──────────────────┐
│         决定跑哪些阶段、参数从哪来、结果往哪写         │
└─────────────────────────────────────────────────────┘
        ↓
┌─ 算法层  init / gp / lg ────────────────────────────┐
│  InitialPlacer  {Random, Clustering, Quadratic}     │
│  GlobalPlacer   {ePlace: 密度 + 线长 + Nesterov}     │
│  Legalizer      {Abacus, Macro SA}                  │
└─────────────────────────────────────────────────────┘
        ↓                              ↓
┌─ 数据层  PlaceDB ─────┐   ┌─ 数值内核  numeric ─────┐
│  Module/Pin/Net/Row   │   │  PoissonSolver (DCT)    │
│  CoreRegion/ChipRegion│   │  SparseSolver (BiCGSTAB)│
│  HPWL / 面积 / 重叠查询│   │  Nesterov / BinGrid     │
└───────────────────────┘   └─────────────────────────┘
        ↑
┌─ IO 层  io / plot ──────────────────────────────────┐
│  BookShelf R/W · GDSII W · CImg 渲染 · (LEF/DEF)     │
└─────────────────────────────────────────────────────┘
```

### 3.2 依赖铁律

> **三个算法阶段互不依赖，只通过 PlaceDB 通信。**

初始布局不知道全局布局的存在，全局布局也不知道自己的输入是随机撒的还是二次规划解出来的。
这条约束换来的是：阶段可以任意跳过、替换、重排，可以从任意中间 `.pl` 续跑。

这不只是洁癖。全局布局在 adaptec1 上跑一次是分钟级的，调试密度梯度符号错误时，
绝对不想每次都重新解析 21 万个 module 再重跑一遍二次规划。所以 CLI 必须支持
`--stage=gp --input-pl=results/init.pl` 直接从中间态启动。

### 3.3 交叉验证：easyPlace 独立收敛到了同一形态

仓库中的 `baseline_/` 是 **easyPlace**（上海科技大学 Ziang Ge / Yikai Liu 对 ePlace 与 ePlace-MS
的重实现）。它的结构与上述设计高度一致，可作为架构合理性的旁证：

| 本文档的设计 | easyPlace 的对应实现 |
| --- | --- |
| ISPD 风格 CLI | `./ePlace -aux ... -targetDensity ... -targetOverflow ...` |
| 阶段可独立启停 | `-noQP` `-nomGP` `-nomLG` `-nocGP` `-noLegal` 五个跳过开关 |
| 数值内核与布局语义解耦 | 独立的 `FFT/` 与 `Optimization/` 模块 |
| 内核可单独测试 | `parser_test.cpp` `qplace_test.cpp` `binDensity_test.cpp` `ePlace_test.cpp` |
| 分阶段可视化 | `-fullPlot` 逐迭代出图 |
| 依赖随仓库分发 | `Library/` 内置 CImg 与 eigen-3.4.0 |

差异之处主要在：easyPlace 用 `arghandler` 手写参数解析而非配置文件；没有独立的检查器；
数据结构是传统 AoS。这几点正是本文档下一节要重点改进的方向。

> **重要**：easyPlace 并未覆盖全部课程任务——**任务 4 只实现了三种初始布局中的一种
> （随机布局是死代码、聚类完全缺失），任务 6 完全没有 GDSII 导出**，
> 且其二次布局的 Y 方向边界判定存在一个实质性 bug。
> 完整的覆盖度对照、缺陷清单与优化建议见
> [02-baseline 代码评估.md](02-baseline%20代码评估.md)。

> **说明**：`baseline_/` 已在 `.gitignore` 中，仅作为学习与对照基准，
> 本项目应独立实现，不直接复用其代码。

## 4. 六个关键决策

架构图谁都会画，下面这几条才是决定"两周做完还是两个月做不完"的地方。

### 决策 1：数值内核必须完全不认识"单元"这个概念

`PoissonSolver` 的接口应该长这样：

```cpp
class PoissonSolver {
public:
    PoissonSolver(int mx, int my);
    // 输入 m×m 密度网格，输出电场与电势。仅此而已。
    void solve(const float* density, float* ex, float* ey, float* potential);
};
```

它不接受 `PlaceDB`，不知道什么是 macro、什么是 filler。这样就能拿解析可验证的输入去测它：
塞一个高斯分布进去，检查电场是否指向外侧、边界法向分量是否为 0、DC 是否被消掉。

**这是整个项目里对调试效率影响最大的决策。** ePlace 的 DCT 部分是符号错误和缩放错误的重灾区，
而这类错误在整个布局器串起来跑的时候是**看不出来的**——你只会看到单元乱飘，
然后完全无法定位是密度、线长、λ 还是步长的问题。`SparseSolver` 同理，必须能脱离布局问题单独测。

### 决策 2：坐标约定只允许存在一个，转换只发生在 IO 层

BookShelf 的 `.pl` 存的是**左下角**坐标，二次规划的未知量是**中心**坐标，
CImg 绘图又要翻转成**屏幕**坐标系。这三套约定混在一起是本项目最高频的 bug 来源。

**规则**：

- `PlaceDB` 内部**只存中心坐标**（`double`）
- 左下角 / 右上角只以 `getLL()` / `getUR()` 这类派生查询的形式暴露
- 左下角 ↔ 中心的换算**只在 BookShelf reader/writer 里各出现一次**
- Y 轴翻转**只在 CImg renderer 里出现一次**
- 算法代码里任何出现 `0.5 * width` 的地方都应被视为可疑

### 决策 3：数据布局——对象模型给人看，扁平数组给循环跑

课程资料给的是 `vector<Module*>` 这类经典 OO 结构，用来解析、调试、打印很舒服。
但全局布局的内层循环要在 944k 个 pin 和 211k 个 node 上跑几百轮，
指针追逐的 cache miss 会慢一个数量级，而且没法安全地上 OpenMP。

**方案：两者都要，分工明确。**

- `Module` / `Pin` / `Net` 对象作为"数据库记录"，负责解析、IO、可视化、调试输出
- 进入优化循环前**扁平化成 SoA 数组**（`vector<float> x, y, w, h, area`，按整数 ID 索引）
- 算完再写回

这层转换是一次性的，成本可忽略，但让内层循环变成纯数组遍历——既 cache 友好，
又能直接 `#pragma omp parallel for`。

> 补充：密度累加（多线程往同一个 bin 里加）需要 per-thread 局部网格再规约，
> 不要用原子操作，会严重退化。

### 决策 4：可观测性是一个子系统，不是 printf

全局布局是会震荡、会发散、会安静地收敛到垃圾的迭代数值过程。**没有逐迭代指标就是在盲调。**

`MetricsSink` 应与 PlaceDB 一样是贯穿全流程的一等公民，每轮记录：

- HPWL
- 密度溢出率 τ
- 惩罚系数 λ
- 平滑参数 γ
- 步长 α
- 梯度范数（线长 / 密度分别记）
- 最大单元位移

全部落到 CSV。配套的是**每 N 轮出一张 PNG**。这个东西性价比高到不合理：
既是最有效的调试手段（单元塌成一团 / 炸到边界 / 卡在 bin 边界不动，看一眼图就知道，
看数字要猜半天），又直接是答辩上最能打的演示素材。为了调试本来就要做，顺手就成了 demo。

### 决策 5：参数进配置文件，不进源码

`targetDensity`、`maxIter`、`targetOverflow`、`MIN_DISTANCE`、bin 维度、
`ΔHPWL_REF = 3.5e5` ⋯⋯ 这类魔数有几十个，而且**必然要反复调**。

JSON / TOML 配置 + CLI 覆盖。否则每次调参都要重编译，实验矩阵根本跑不起来。

### 决策 6：检查器必须独立于布局器

`superplace-check` 单独一个二进制，读 `.aux` + `.pl`，报告：

- 单元间重叠面积与重叠对数
- 越出 CoreRegion 的单元数
- 未对齐到 row / site 的单元数
- HPWL

**关键在于它不能复用布局器的几何代码**——共享代码就会共享 bug，检查就失去意义。
ISPD 竞赛就是这么评测的，任务 7 的合法化验收也直接靠它。

### 5.2 统一的阶段接口

编排层其实很小，整个流程可以收敛成一个接口：

```cpp
class PlacementStage {
public:
    virtual void run(PlaceDB& db, const Config& cfg, MetricsSink& sink) = 0;
    virtual std::string name() const = 0;
    virtual ~PlacementStage() = default;
};
```

`main` 里就是：

```cpp
for (auto& stage : pipeline) {
    ScopedTimer t(sink, stage->name());
    stage->run(db, cfg, sink);
    dumpSnapshot(db, cfg, stage->name());   // 每阶段自动落 .pl + .png
}
```

CLI 只负责决定 `pipeline` 里放哪几个 stage。跑完整流程、只跑解析、从中间续跑、
三种初始布局对比，全都是同一套代码换个 pipeline 组装。

## 6. 高杠杆取巧点

### 6.1 GDSII 分层输出

把 macro、标准单元、filler、terminal、core 边界、site row 写到**不同的 GDSII layer** 上。

KLayout 的图层开关立刻就变成一个专业级交互查看器——能缩放、能测距、能单独看 filler 分布、
能叠加边界。**一行 GUI 代码都不用写，白嫖一个比自己造的 viewer 好得多的前端。**

任务 6 要求的两种展示方式里，这一种的投入产出比远高于 CImg。

### 6.2 实验矩阵脚本化

任务 4 要求从"连接保持能力、时间复杂度、面积控制、适用规模"四个维度比较三种初始布局。

与其手工跑多次记数字，不如写成 `scripts/run_matrix.py`，一次跑完
`{3 种方法} × {3 个 benchmark}`，直接吐出报告里能用的表格和折线图。
这个脚本在开发期间也会天天用来做回归测试。

## 7. GUI 前端设计与选型

### 7.1 定位：观察器 + 调试器，不是图形化启动器

如果 GUI 只是给参数配几个输入框再加一个"运行"按钮，它没有创造任何价值——
只是把 `--target-density 0.9` 换成了 spin box，还搭进去几千行代码。

GUI 真正能提供而 CLI 提供不了的只有两件事：

**（1）交互式空间探索。** 布局结果是二维空间数据，静态 PNG 一旦导出就只有那一个视角、
一个配色。而真正要回答的问题是"这块密度为什么这么高""这几个 macro 周围的单元被谁拉过去了"
"filler 铺匀了没有"——这些需要缩放、平移、按类型开关图层、按属性着色、
点选单元高亮其所有 net。

**（2）实时观察迭代过程。** 这是杀手锏。一边看单元在电场里散开，一边同步看 HPWL 与 τ 曲线跳动，
还能暂停、单步、拖时间轴回看。调 ePlace 时价值极高，答辩时也最能打。

> 注意：任务 6 要求的 CImg 不会被 GUI 取代。CImg 用于**无头**写 PNG（不需要开窗口），
> 批量实验与生成 GIF 都靠它，与交互式查看器是两条正交的路。

### 7.2 环境实测结论（关键）

在本机 WSL2 环境实测：

| 项目 | 结果 |
| --- | --- |
| WSLg | ✅ 存在（`/mnt/wslg`，`DISPLAY=:0`，`WAYLAND_DISPLAY=wayland-0`） |
| 默认 OpenGL 渲染器 | ⚠️ `llvmpipe` 软件光栅化，`Accelerated: no` |
| GPU 直通库 | ✅ `/usr/lib/wsl/lib/libd3d12.so`、`libd3d12core.so` 齐全 |
| mesa d3d12 驱动 | ✅ `d3d12_dri.so` 已安装 |
| 切换后 | ✅ `D3D12 (NVIDIA GeForce RTX 4060 Laptop GPU)`，`Accelerated: yes` |

**必须做的一步**：默认走的是 CPU 软渲染，画 21 万个矩形会卡成幻灯片。加环境变量切到硬件加速：

```bash
export GALLIUM_DRIVER=d3d12
```

建议写进 `~/.bashrc` 或项目启动脚本。切换后有独显撑着，渲染压力可以忽略。

### 7.3 框架选型对比

| 框架 | 优势 | 代价 | 适用判断 |
| --- | --- | --- | --- |
| **Dear ImGui + GLFW + OpenGL** | 引入成本近乎为零（vendor 进仓库或 CMake `FetchContent`，**无需 apt 装任何东西**）；即时模式，加控件就是一行代码；ImPlot 画收敛曲线开箱即用 | 观感像调试工具而非商业软件；文件对话框需额外接 `ImGuiFileDialog` | ⭐ **首选** |
| **Qt 6 Widgets** | KLayout 与 OpenROAD GUI 都是 Qt，最"根正苗红"；dock / 菜单 / 表格 / 文件对话框开箱即用 | `qt6-base-dev` 几百 MB；moc 让构建复杂；学习曲线真实存在 | 想要产品感时选它 |
| **PySide6 + pybind11** | 本来就要写 Python 实验脚本，是自然延伸；PyQtGraph 2D 性能出乎意料地好；开发速度快数倍 | 引入第二套工具链；打包分发麻烦 | 团队 Python 更熟时的高性价比折中 |
| **浏览器前端（C++ WebSocket + WebGL）** | 单位时间视觉产出最高；图表生态（ECharts/Plotly）远比 C++ 成熟；**彻底绕开 WSL2 显示问题**（服务在 WSL，浏览器在 Windows，localhost 自动转发） | 严格说不是"桌面软件"；需前端能力 | 团队有前端能力时的最优解 |
| Tauri | 可把 Web UI 包成真桌面应用 | Rust 外壳 + C++ sidecar，复杂度对课设过高 | 不推荐 |
| wxWidgets / FLTK / Electron / Nuklear | — | 2D 画布弱 / 太原始 / 太重 / 无优势 | 不推荐 |

**推荐理由（ImGui）**：它是即时模式 GUI，本来就为工具和调试界面设计，
而我们要做的恰恰是一个工具。加个图层开关字面意义上就是
`ImGui::Checkbox("Fillers", &showFillers);`。这种迭代速度 Qt 给不了。
更重要的是零系统依赖，不存在"队友环境装不上"的问题。

> **Qt 的坑（如果选它）**：画布**千万不要用 `QGraphicsView` + 每单元一个 `QGraphicsItem`**。
> 21 万个 QGraphicsItem 会直接压垮它，光是对象构造和场景索引就要几秒。
> 正确做法是用 `QOpenGLWidget` 自己画——那其实又回到了和 ImGui 一样的渲染逻辑，
> Qt 只负责外面那圈窗口和控件。

### 7.4 真正的技术难点：21 万个矩形怎么画

这是唯一会决定 GUI 好不好用的技术问题，**且与框架选择无关**。

**（1）绝对不能走场景图路线**——不要给每个单元创建一个对象。

**（2）正确解法是 GPU 实例化渲染**：把所有单元的 `(x, y, w, h, type)` 打包成一个顶点缓冲，
每帧一次 `glDrawArraysInstanced`，一个 draw call 画完全部。RTX 4060 处理这个量级是微秒级，
上百万单元也不会喘。位置变了就更新缓冲区（211k × 2 float = 1.7 MB，
`glBufferSubData` 开销可忽略）。

**（3）亚像素问题**：全芯片视角下绝大多数标准单元只有亚像素大小，硬画出来是一团摩尔纹噪点。
需要按缩放级别切换渲染模式——远景画 bin 密度热力图（这个数据 ePlace 本来就在算，直接复用），
拉近到一定倍率再切回真实矩形。**KLayout 就是这么做的。**

### 7.5 架构接入方式

分层不变，GUI 是与 CLI 平级的第二前端：

```
        libsuperplace  (db / io / numeric / init / gp / lg / plot)
              ↑                    ↑                    ↑
        superplace (CLI)    superplace-gui       superplace-check
```

唯一需要新增的机制是**线程安全的位置快照**：布局器在 worker 线程持续修改坐标，
GUI 主线程每帧要读一份一致数据，两者不能直接碰同一块内存。

做法是**双缓冲**：worker 每轮迭代结束后把位置数组写进备用缓冲，然后原子交换指针；
GUI 只读当前缓冲。

> 这里正好印证决策 3 的价值：位置若是扁平 `vector<float> x, y`，
> 快照就是一次 1.7 MB 的 `memcpy`，几十微秒，每帧做都无所谓；
> 若是 `vector<Module*>`，就得遍历指针逐个拷贝，还要操心对象生命周期与半更新状态。
> **GUI 的存在反过来强化了引擎内部该用扁平数组的理由。**

另建议 worker 通过回调把每轮指标推给 `MetricsSink`，GUI 与 CSV writer 都从该 sink 订阅。
这样命令行跑和界面跑拿到的是同一份数据，不会出现"图上显示的和日志记的对不上"这种极难排查的问题。

**总原则：架构一次搭好，但不要一次实现完。** 骨架的价值恰恰在于
**每个任务完成时都有一个能跑、能出图、能验证的完整产物**。
