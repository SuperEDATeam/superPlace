## 1. 三条约束，以及它们为什么不冲突

这套方案是从三条约束倒推出来的，其中前两条看起来和第三条有矛盾：

1. **与算法部分耦合要低。** `src/` 是迭代了几个月的东西，数值内核里全是符号与缩放的坑
   （05 §5.5.7 那几条"写反了会越跑越挤"的注释）。前端开发**不应该有能力**改坏它——
   不是靠约定，而是靠结构上做不到。
2. **前端要能脱离算法依赖独立测试。** 同伴不该为了看一眼界面，先把 FFTW、Eigen、
   libpng、OpenMP 装通再等几十秒编译。
3. **不对 GUI 的水平和质量作让步。** 包括 [01 §7.1](01-架构设计与技术选型.md)
   说的那个杀手锏——**一边跑布局一边看单元在电场里散开**。

矛盾在于：实时观察意味着 GUI 进程里得跑着布局器，那不就必须链接 `libsuperplace` 吗？

**答案是：把"链接算法"从一个全局事实降级为一个可选的构建模式。**
UI 与渲染层只认一个纯虚接口 `IPlacementSource`；离线模式注入读文件的实现，
实时模式注入包引擎的实现。同伴日常构建的是离线版，`ldd` 里连 `libgomp` 都没有；
需要实时时多给一个 CMake 变量，就多出一个集成版可执行文件。

**三条约束同时成立，没有一条被牺牲。** 下面两节是这句话的具体兑现方式。

## 2. 架构：单向依赖 + 一个接缝

### 2.1 依赖方向是单向的

```
         ┌──────────── gui/（独立顶层 CMake 工程）────────────┐
         │  viz_core：场景模型 / 渲染 / 相机 / 面板            │
         │            ↑ 只认 IPlacementSource                 │
         │   ┌────────┴────────┐                              │
         │   │                 │                              │
         │ BundleSource    LiveSource ····──────────┐         │
         │ （读文件，零依赖） （可选编译）            │         │
         └───────────────────────────────────────── │ ────────┘
                                                     ↓ 可选
                                              libsuperplace（算法侧）
```

**根目录的 `CMakeLists.txt` 里没有任何一行提到 `gui`**（可自行 `grep gui CMakeLists.txt` 验证）。
依赖只有一个方向：gui 可以去找算法侧，算法侧永远不知道 gui 存在。

由此得到一个**结构性保证**：在 `gui/` 里做任何改动，都不可能让
`cmake --build build` 或 `ctest` 失败。这比"请不要改 src/"这种口头约定可靠得多。

### 2.2 两种构建模式

```bash
# 独立模式 —— 同伴日常开发用，零算法依赖
cmake -S gui -B gui/build && cmake --build gui/build -j
#   产出 superplace-viz

# 集成模式 —— 需要实时观察时才用，要求算法侧已构建
cmake -S gui -B gui/build-int -DSUPERPLACE_ROOT=$PWD/build
#   额外产出 superplace-gui
```

两个产物的 `ldd` 对比，就是"低耦合"的具体形态：

| | `superplace-viz`（独立） | `superplace-gui`（集成） |
| --- | --- | --- |
| libsuperplace | ❌ | ✅ |
| OpenMP / FFTW / libpng / Eigen | ❌ **一个都没有** | ✅ 全部需要 |
| 能离线看结果 | ✅ | ✅ |
| 能实时看迭代 | ❌ | ✅ |

### 2.3 唯一的接缝：`IPlacementSource`

```cpp
class IPlacementSource {
public:
    virtual const SceneInfo&    scene()    const = 0;   // core/chip/计数，不变
    virtual const NodeGeometry& geometry() const = 0;   // w/h/flags，不变
    virtual const MetricsTable* metrics()  const = 0;
    virtual int  frameCount() const = 0;                // 实时源会不断变大
    virtual bool frame(int index, FrameView& out) = 0;
    virtual bool isLive() const { return false; }
    virtual bool poll() { return false; }               // 有新帧则 true
};
```

形式上这就是算法侧"决策 7 Backend Strategy"的同一套路：纯接口 + 工厂，实现藏在各自的 `.cpp`。

收益很具体：

- 同伴日常只对着 `BundleSource`，**连算法侧的头文件都不需要 include**；
- 接实时模式时新增一个 `LiveSource`，**UI 代码一行都不用改**（已验证）；
- 算法侧重构 `PlaceDB` 时，**波及范围是 `live_source.cpp` 这一个文件**——
  它是整个 gui 工程里唯一 include 算法侧头文件的翻译单元。

### 2.4 实时模式是怎么接上的

`LiveSource` 的全部工作量约 170 行：

1. 用引擎的 `BookshelfReader` 读设计，`initializeFillers` 插 filler；
2. 起一个 worker 线程跑 `makeInitialPlacer` + `EPlace::run`；
3. 挂上引擎**已经存在**的逐迭代回调 `EPlace::setIterCallback`
   （M3 为出 PNG 而加的，这里直接复用），每 `stride` 轮把坐标抓成一帧；
4. 帧列表用 mutex 保护，UI 线程通过 `poll()` 感知新帧。

> 注意这里**没有**改动算法侧任何代码——`setIterCallback` 是现成的接口。
> 这也说明 M3 当初把出图做成回调而不是直接调 `plot/` 是对的。

实跑验证（adaptec1）：worker 线程里的引擎收敛到 **HPWL = 7.20909e7**，
与 M3 记录的 7.20913e7 一致，UI 侧同时拿到 32 帧并正常显示。

## 3. 数据契约 `superplace-viz/1`

离线模式读的文件格式。它同时也是**框架无关的资产**——将来若要换 Qt 或做 Web 版，
契约可以原样复用，重写的只是渲染与 UI 那层。

### 3.1 目录结构

```
<bundle>/
├── scene.json        元数据（小、人可读，唯一的 JSON）
├── geom.bin          静态几何：每节点 (w, h)
├── flags.bin         静态类别：每节点 1 字节标志位
├── frames/
│   ├── f0000.bin     位置快照：x[N] 紧接 y[N]
│   └── …
├── names.txt         可选：每行一个节点名，供检视面板用
├── metrics.csv       引擎产物原样复制（可选）
└── summary.json      引擎产物原样复制（可选）
```

**为什么几何与位置分开存**：`(w, h)` 和类别整场不变，读一次就够；
位置每帧都变，是动画的全部载荷。混在一起会让每帧的 I/O 翻倍。

### 3.2 `scene.json`

```json
{
  "format": "superplace-viz/1",
  "benchmark": "newblue1",
  "nodeCount": 330474,
  "core":      { "lx": 609,  "ly": 616,  "hx": 11783, "hy": 11776 },
  "chip":      { "lx": 0,    "ly": 0,    "hx": 12364, "hy": 12364 },
  "rowHeight": 12.0,
  "rows": 930,
  "flagBits":  { "macro": 1, "fixed": 2, "filler": 4, "ni": 8 },
  "hasMetrics": true,
  "frames": [
    { "file": "frames/f0000.bin", "stage": "input", "label": "input (newblue1.pl)" },
    { "file": "frames/f0001.bin", "stage": "init",  "label": "init (newblue1.init.pl)" },
    { "file": "frames/f0002.bin", "stage": "gp",    "label": "gp (newblue1.gp.pl)" }
  ]
}
```

> ⚠️ **`core` 与 `chip` 往往不一样，视野要按 `chip` 来 fit。**
> 真实设计的 I/O pad 大量位于 core **之外**（newblue1 的 337 个固定终端就在 core 外一圈）。
> 只按 core 适应窗口会把它们裁掉。

### 3.3 二进制文件布局

**全部小端、紧凑排列、无文件头**，直接 `read()` 进 `float` 数组即可，零解析开销。

| 文件 | 元素类型 | 长度 | 布局 |
| --- | --- | --- | --- |
| `geom.bin` | `float32` | `2 × nodeCount` | **交错**：`w₀ h₀ w₁ h₁ …` |
| `flags.bin` | `uint8` | `nodeCount` | `flags₀ flags₁ …` |
| `frames/*.bin` | `float32` | `2 × nodeCount` | **分块**：先 `x₀…x_{N-1}`，再 `y₀…y_{N-1}` |

节点下标在所有文件、所有帧中是同一套且恒定：第 `i` 个节点的宽是 `geom[2i]`、
标志是 `flags[i]`、在第 f 帧的中心是 `(frame.x[i], frame.y[i])`。

### 3.4 坐标约定（最容易出错的一条）

> **bundle 里的位置一律是【中心坐标】，不是左下角。**

BookShelf 的 `.pl` 用左下角，引擎内部用中心（算法侧的"铁律 2"），
bundle 跟随引擎用中心，换算只发生在 `make_viz.py` 里一处。
Y 轴向上为正，**翻转只应发生在最终投影那一步**。

### 3.5 节点类别与配色

`flags.bin` 的每个字节是位掩码，判定顺序必须固定：

```cpp
if (flags & 4) kind = Filler;        // F_FILLER
else if (flags & 2) kind = Fixed;    // F_FIXED（固定终端 / 已合法化的宏）
else if (flags & 1) kind = Macro;    // F_MACRO
else kind = Cell;
```

`F_NI`（bit 3）标记**零面积**的 I/O 引脚，`w = h = 0`，渲染时必须跳过。

配色与引擎的 PNG 输出（`src/plot/cimg_renderer.cpp`）一致，
这样界面和报告里的图看起来是同一个东西：

| 类别 | 颜色 | 默认可见 |
| --- | --- | --- |
| 标准单元 | 红 `#dc3c3c` | ✅ |
| 宏单元 | 橙 `#f59628` | ✅ |
| 固定终端 | 蓝 `#3d6edc` | ✅ |
| Filler | 绿 `#4fbe5a` | ❌（数量和单元同量级，默认开会糊掉） |

### 3.6 体积预算

每帧 = `nodeCount × 8` 字节。这是设计加载策略的唯一依据：

| 设计 | 节点数 | 单帧 | 40 帧动画 |
| --- | --- | --- | --- |
| 合成样本 | 8,080 | 65 KB | 2.7 MB |
| adaptec1 | 211k | 1.7 MB | 68 MB |
| newblue1 | 330k | 2.6 MB | 106 MB |
| bigblue4 | 2.18M | 17 MB | 700 MB |

**帧必须按需加载。** `BundleSource` 已实现按需读 + 最多缓存 24 帧的 LRU。
百万级设计要配合 `make_viz.py --max-frames` 抽样。

### 3.7 怎么生成 bundle

```bash
# 合成样本：不需要任何 benchmark 数据
python3 scripts/make_viz.py --synthetic --out gui/sample-data/synthetic

# 真实数据：需要 benchmark 原件 + 一次引擎运行的 results 目录
python3 scripts/make_viz.py --aux benchmarks/ispd2006/newblue1/newblue1.aux \
                            --result results/audit/newblue1 --out /tmp/viz/newblue1

# 校验 bundle 是否合规（格式争议由程序裁决，不靠人对文档）
python3 scripts/make_viz.py --verify gui/sample-data/synthetic
```

`make_viz.py` 是只读的——它读 BookShelf 原件与 `results/` 产物，不改引擎一行代码。
因此**引入前端这件事对算法侧的改动量是零**。

合成样本刻意覆盖了前端必须处理的**全部形态**：标准单元、可移动宏、core 外的固定
I/O pad、零面积 `terminal_NI`、filler，以及"从中心一团逐步铺开"的收敛过程。

## 4. 唯一的技术难点：几十万个矩形怎么画

[01 §7.4](01-架构设计与技术选型.md) 已有判断，这里给出已验证的实现要点。

**（1）绝不能一个单元一个对象。** 不要 `QGraphicsItem`、不要每单元一次 draw call。
33 万个对象光构造和场景索引就要几秒。

**（2）正确解法是 GPU 实例化。** 顶点缓冲里只放一个 0..1 的单位方片，
每个单元作为一个"实例"提供 `(cx, cy, w, h, kind)`，一次 `glDrawArraysInstanced`
画完全部。位置变了只需 `glBufferSubData` 覆盖实例缓冲（330k × 2 float = 2.6 MB）。

**（3）亚像素保护是正确性要求，不是优化。** 全芯片视角下标准单元只有零点几个像素，
原样画会碎成一片摩尔纹噪点，看起来像"布局是坏的"。顶点着色器里把屏幕空间边长
撑到至少 `uMinPx`：

```glsl
vec2 pxSize = aSize * uView.z;
vec2 size = aSize * max(vec2(1.0), uMinPx / max(pxSize, vec2(1e-6)));
```

顺带一个好性质：零面积的 `terminal_NI` 节点 `aSize = 0`，`0 × 任何数 = 0`，
退化四边形不产生任何片元，GPU 自己就消掉了——不需要额外的分支。

**（4）图层开关不要拆 draw call。** 直接把该类的 alpha 置 0，片元里 `discard`。
33 万实例下 GPU 完全不在乎这点无效片元，而按类拆分会让代码复杂不少。

**（5）进一步的 LOD（后续优化）。** 拉远到一定程度改画 bin 密度热力图而不是真实矩形，
KLayout 就是这么做的。密度场可以在查看器里由位置现算，不必加进 bundle。

## 5. 已实测的基线数据

下面的数字都是在本机实跑出来的，不是估计。改动渲染路径后可以用
`--bench` 复测，防止性能悄悄退化。

### 5.1 渲染性能

```bash
cd gui && GALLIUM_DRIVER=d3d12 ./build/superplace-viz /tmp/viz/newblue1 --bench 300
```

| 数据集 | 节点数 | 中位 | p95 | 折合 |
| --- | --- | --- | --- | --- |
| 合成样本 | 8,080 | 0.90 ms | 1.63 ms | 1112 fps |
| **newblue1** | **330,474** | **1.80 ms** | **3.14 ms** | **557 fps** |

视口 1600×980，**每帧都切换数据**（含位置上传），所以这是动画播放的真实负载。
`--bench` 会自动关掉 vsync，否则帧时间被钳在 16.7 ms，测不出余量还剩多少。

### 5.2 图形环境（WSL2）

| 项目 | 结果 |
| --- | --- |
| 默认 OpenGL | ⚠️ `llvmpipe` 软件光栅化，`Accelerated: no` |
| `GALLIUM_DRIVER=d3d12` | ✅ `D3D12 (NVIDIA GeForce RTX 4060 Laptop GPU)`，OpenGL **4.6 Core** |

> **这个环境变量是必须的**，否则 33 万个矩形会卡成幻灯片。
> 建议写进 `~/.bashrc`：`export GALLIUM_DRIVER=d3d12`

### 5.3 构建产物

| 目标 | 体积 | 链接了算法侧依赖吗 |
| --- | --- | --- |
| `superplace-viz` | 6.9 MB | ❌ 零个（`ldd` 只有 GL/X11/glfw/libc） |
| `superplace-gui` | 7.3 MB | ✅ libsuperplace + libgomp + libfftw3f + libpng |

## 6. 工作边界：哪些能改，哪些绝对不要碰

### ✅ 完全属于前端，随便改

```
gui/                  前端全部代码、第三方 vendor、样本数据
```

### ⛔ 不要修改

```
src/          算法与引擎（C++）
test/         算法单元测试
CMakeLists.txt / test/CMakeLists.txt
configs/      引擎运行配置
work_report/  设计文档（本文除外）
```

### ⚠️ 需要先商量

```
scripts/make_viz.py        转换层。改它等于改契约，必须双方确认，
                           且改完 --verify 要对所有现存 bundle 通过
gui/src/viz/live_source.cpp 唯一 include 算法侧头文件的地方。
                           算法侧接口变了要同步改，但只需改这一个文件
```

**结构上的保证**：`gui/` 不被根 `CMakeLists.txt` 引用，既不参与 C++ 主构建也不参与
`ctest`。前端目录里的任何改动都**不可能**让算法侧构建或测试失败。

**建议的协作方式**：前端在独立分支（如 `feat/gui`）上开发，
PR 的改动文件若出现 `gui/` 和 `scripts/make_viz.py` 之外的路径，默认打回。

## 7. 快速上手

### 7.1 装依赖（一次性）

**独立模式（同伴日常开发，只需要这些）：**

```bash
sudo apt install -y libglfw3-dev libgl1-mesa-dev libx11-dev \
                    libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev
echo 'export GALLIUM_DRIVER=d3d12' >> ~/.bashrc && source ~/.bashrc
```

| 包 | 用途 |
| --- | --- |
| `libglfw3-dev` | 窗口与输入。CMake 走 `find_package(glfw3 3.3 REQUIRED)` |
| `libgl1-mesa-dev` | OpenGL 开发头文件（系统里只有运行时 `libGL.so.1` 是不够的） |
| `libx11-dev` 及四个 `libx*-dev` | GLFW 在 Linux 上的编译期依赖 |

**注意这里没有 FFTW / Eigen / libpng / OpenMP**——那些是算法侧的依赖，前端不需要。
ImGui 与 ImPlot 已 vendor，`nlohmann/json` 复用仓库根目录那份，都不必安装。

**集成模式额外需要**（只有要跑实时模式时才装；其实就是算法侧那套依赖，
如果主工程已经能构建，这些就都在了）：

```bash
sudo apt install -y pkgconf libpng-dev libeigen3-dev libfftw3-dev
```

`libsuperplace` 是静态库，它的传递依赖得由使用方链上，所以集成版才需要这些。

**可选小工具**：`--screenshot` 存的是 PPM，转 PNG 用
`python3 -c "from PIL import Image; Image.open('a.ppm').save('a.png')"`，
需要 `python3-pil`。

ImGui（docking 分支）与 ImPlot 已经 vendor 在 `gui/third_party/`，不需要联网。
这与项目既有做法一致（根目录 `third_party/` 里的 CImg 与 nlohmann 也是 vendor 的，
见 [01 §9.2](01-架构设计与技术选型.md)）。

> **为什么不用 CMake FetchContent 现拉**：本机到 GitHub 的 git clone 与 codeload
> 实测均不通（clone 100 秒零进展、tarball 90 秒 0 字节）。vendor 之后 clone 仓库
> 即可构建，比配置时现拉可靠得多。

### 7.2 构建并运行

```bash
cmake -S gui -B gui/build -DCMAKE_BUILD_TYPE=Release
cmake --build gui/build -j
cd gui && ./build/superplace-viz            # 默认加载 sample-data/synthetic
```

常用参数：

| 参数 | 用途 |
| --- | --- |
| `<bundle 目录>` | 加载指定 bundle |
| `--frame N` | 启动时跳到第 N 帧，`-1` = 最后一帧 |
| `--bench N` | 渲染 N 帧、报告耗时后退出（自动关 vsync），用于性能回归 |
| `--screenshot out.ppm` | 保存截图（PPM，可用 PIL 转 PNG） |
| `--shot-after 秒` | 正常跑 UI，到点自动截图并退出，用于脚本化出图 |

### 7.3 实时模式（可选）

前置条件：算法侧已构建出 `build/libsuperplace.a`，且 §7.1 的集成模式依赖已装。

```bash
cmake -S gui -B gui/build-int -DSUPERPLACE_ROOT=$PWD/build
cmake --build gui/build-int -j
cd gui && ./build-int/superplace-gui ../test_data/adaptec1/adaptec1.aux --stride 10
```

`--stride N` 控制每 N 轮发布一帧。调小更流畅，但内存按 `节点数 × 8 字节/帧` 线性增长。

> ⚠️ **当前只跑 mGP 一个阶段**，没有 mLG / FILLERONLY / cGP，也没有暂停与单步。
> 见 §8.2 缺口 #3。

### 8.3 四个已经踩过的坑（改渲染或布局时留意）

这几个都是花了实打实的时间定位出来的，写在这里省得再踩一次。

**（1）`PassthruCentralNode` 不能装窗口。** 它的语义是"中央节点**为空时**才透出背景"。
一旦把窗口停靠进中央节点，dockspace 会照常铺一层 `WindowBg`，把底下的 GL 内容
整个盖掉——现象是画布全白而 `glGetError()` 干净。**正确用法是让中央节点保持空**，
用 `DockBuilderGetCentralNode()` 取它的矩形，自己往那块区域画。
给窗口加 `NoBackground` 并不能解决。

**（2）dockspace 的 id 必须用 `DockSpaceOverViewport()` 的返回值。**
自己拼 `GetID("DockSpaceViewport_11111111")` 猜是错的，
`DockBuilderGetCentralNode()` 会返回 `nullptr`，画布静默地停在 1×1 不报任何错。

**（3）`fit` 不能在第一帧做。** 停靠布局在第一帧还没算好，此时画布只有几十像素，
照着它算出来的比例会小两个数量级（实测 0.002 px/unit，正确值约 0.3），
内容整个飞到视野外。要等画布尺寸稳定（`> 32 px`）再 fit。

**（4）GL 上下文就绪之前不能上传几何。** 集成版在 `run()` **之前**就注入数据源，
那时 `glLoad()` 还没跑、函数指针全是空的，直接段错误。
`App` 因此把上传推迟到 `uploadGeometry()`，由主循环在上下文就绪后触发——
接口不应该靠调用顺序来保证正确性。

## 9. 开发路线与验收标准

三个阶段，每阶段都是独立可交付的东西。

### 阶段一：静态查看器（骨架已覆盖基本交互，缺检视能力）

| 项 | 判据 |
| --- | --- |
| 加载 | 合成样本与 newblue1 均能加载；格式不符时给出可读错误而非白屏 |
| 渲染正确 | 四类节点颜色正确；零面积 `F_NI` 被跳过；纵横比不变形 |
| 视野 | 按 `chip` 而非 `core` 适应窗口；缩放以光标为锚点 |
| 性能 | 330k 节点交互流畅。基线：中位 1.80 ms/帧 |
| 图层 | 四个开关即时生效；filler 默认关 |

**待补**：§8.2 的缺口 #1 #2（两处死代码，适合热身）、#9 窗口 resize 自适应、
#11 快捷键与比例尺、#12 单元测试。

### 阶段二：检视与联动（价值最高）

| 项 | 判据 |
| --- | --- |
| 点选（缺口 #4） | 点中一个单元，显示名字、尺寸、类别、位置。需自建空间索引，33 万节点不能线性扫 |
| 总览面板（缺口 #1） | 读 `summary.json`，展示最终 HPWL、τ、各阶段耗时、宏重叠、可移动宏数 |
| 曲线联动（缺口 #10） | 拖时间轴，曲线游标同步；点曲线也能跳到对应帧 |
| 密度热力图（缺口 #7） | 由当前帧位置现算 bin 密度并叠加，兼作远景 LOD |
| 两帧对比（缺口 #8） | 叠加两帧，用颜色或箭头表示单元位移 |

### 阶段三：实时与打磨

| 项 | 判据 |
| --- | --- |
| 实时模式补齐（缺口 #3） | 四阶段 mGP→mLG→FILLERONLY→cGP；可暂停、单步、回看 |
| 网表高亮（缺口 #5） | 点选单元后高亮其所有 net（需 bundle 增加 CSR 连接性） |
| 属性着色（缺口 #6） | 可切换按密度 / 按位移 / 按 net 数着色 |
| 交付 | 窗口布局持久化、主题、状态栏、关于对话框 |

- `grep gui CMakeLists.txt` 无输出（结构保证未被破坏）
- `cmake --build build && ctest --test-dir build` 仍全绿
- `python3 scripts/make_viz.py --verify` 对所有提交的 bundle 返回 0
