## 1. 三条约束，以及它们为什么不冲突

这套方案是从三条约束倒推出来的，其中前两条看起来和第三条有矛盾：

1. **与算法部分耦合要低。** `src/` 是迭代了几个月的东西，数值内核里全是符号与缩放的坑
   （05 §5.5.7 那几条"写反了会越跑越挤"的注释）。前端开发**不应该有能力**改坏它——
   不是靠约定，而是靠结构上做不到。
2. **前端要能脱离算法依赖独立测试。** 同伴不该为了看一眼界面，先把 FFTW、Eigen、
   libpng、OpenMP 装通再等几十秒编译。
3. **不对 GUI 的水平和质量作让步。** 包括 [01 §7.1](01-架构设计与技术选型.md)
   说的那个杀手锏——**一边跑布局一边看单元在电场里散开**。

矛盾在于：实时观察意味着 GUI 进程里得跑着布局器，那不就必须链接 `libsuperplace` 吗？

**答案是：把"链接算法"从一个全局事实降级为一个可选的构建模式。**
UI 与渲染层只认一个纯虚接口 `IPlacementSource`；离线模式注入读文件的实现，
实时模式注入包引擎的实现。同伴日常构建的是离线版，`ldd` 里连 `libgomp` 都没有；
需要实时时多给一个 CMake 变量，就多出一个集成版可执行文件。

**三条约束同时成立，没有一条被牺牲。** 下面两节是这句话的具体兑现方式。

## 2. 架构：单向依赖 + 一个接缝

### 2.1 依赖方向是单向的

```
         ┌──────────── gui/（独立顶层 CMake 工程）────────────┐
         │  viz_core：场景模型 / 渲染 / 相机 / 面板            │
         │            ↑ 只认 IPlacementSource                 │
         │   ┌────────┴────────┐                              │
         │   │                 │                              │
         │ BundleSource    LiveSource ····──────────┐         │
         │ （读文件，零依赖） （可选编译）            │         │
         └───────────────────────────────────────── │ ────────┘
                                                     ↓ 可选
                                              libsuperplace（算法侧）
```

**根目录的 `CMakeLists.txt` 里没有任何一行提到 `gui`**（可自行 `grep gui CMakeLists.txt` 验证）。
依赖只有一个方向：gui 可以去找算法侧，算法侧永远不知道 gui 存在。

由此得到一个**结构性保证**：在 `gui/` 里做任何改动，都不可能让
`cmake --build build` 或 `ctest` 失败。这比"请不要改 src/"这种口头约定可靠得多。

### 2.2 两种构建模式

```bash
# 独立模式 —— 同伴日常开发用，零算法依赖
cmake -S gui -B gui/build && cmake --build gui/build -j
#   产出 superplace-viz

# 集成模式 —— 需要实时观察时才用，要求算法侧已构建
cmake -S gui -B gui/build-int -DSUPERPLACE_ROOT=$PWD/build
#   额外产出 superplace-gui
```

两个产物的 `ldd` 对比，就是"低耦合"的具体形态：

| | `superplace-viz`（独立） | `superplace-gui`（集成） |
| --- | --- | --- |
| libsuperplace | ❌ | ✅ |
| OpenMP / FFTW / libpng / Eigen | ❌ **一个都没有** | ✅ 全部需要 |
| 能离线看结果 | ✅ | ✅ |
| 能实时看迭代 | ❌ | ✅ |

### 2.3 唯一的接缝：`IPlacementSource`

```cpp
class IPlacementSource {
public:
    virtual const SceneInfo&    scene()    const = 0;   // core/chip/计数，不变
    virtual const NodeGeometry& geometry() const = 0;   // w/h/flags，不变
    virtual const MetricsTable* metrics()  const = 0;
    virtual int  frameCount() const = 0;                // 实时源会不断变大
    virtual bool frame(int index, FrameView& out) = 0;
    virtual bool isLive() const { return false; }
    virtual bool poll() { return false; }               // 有新帧则 true
};
```

形式上这就是算法侧"决策 7 Backend Strategy"的同一套路：纯接口 + 工厂，实现藏在各自的 `.cpp`。

收益很具体：

- 同伴日常只对着 `BundleSource`，**连算法侧的头文件都不需要 include**；
- 接实时模式时新增一个 `LiveSource`，**UI 代码一行都不用改**（已验证）；
- 算法侧重构 `PlaceDB` 时，**波及范围是 `live_source.cpp` 这一个文件**——
  它是整个 gui 工程里唯一 include 算法侧头文件的翻译单元。

### 2.4 实时模式是怎么接上的

`LiveSource` 的全部工作量约 170 行：

1. 用引擎的 `BookshelfReader` 读设计，`initializeFillers` 插 filler；
2. 起一个 worker 线程跑 `makeInitialPlacer` + `EPlace::run`；
3. 挂上引擎**已经存在**的逐迭代回调 `EPlace::setIterCallback`
   （M3 为出 PNG 而加的，这里直接复用），每 `stride` 轮把坐标抓成一帧；
4. 帧列表用 mutex 保护，UI 线程通过 `poll()` 感知新帧。

> 注意这里**没有**改动算法侧任何代码——`setIterCallback` 是现成的接口。
> 这也说明 M3 当初把出图做成回调而不是直接调 `plot/` 是对的。

实跑验证（adaptec1）：worker 线程里的引擎收敛到 **HPWL = 7.20909e7**，
与 M3 记录的 7.20913e7 一致，UI 侧同时拿到 32 帧并正常显示。

## 3. 数据契约 `superplace-viz/1`

离线模式读的文件格式。它同时也是**框架无关的资产**——将来若要换 Qt 或做 Web 版，
契约可以原样复用，重写的只是渲染与 UI 那层。

### 3.1 目录结构

```
<bundle>/
├── scene.json        元数据（小、人可读，唯一的 JSON）
├── geom.bin          静态几何：每节点 (w, h)
├── flags.bin         静态类别：每节点 1 字节标志位
├── frames/
│   ├── f0000.bin     位置快照：x[N] 紧接 y[N]
│   └── …
├── names.txt         可选：每行一个节点名，供检视面板用
├── metrics.csv       引擎产物原样复制（可选）
└── summary.json      引擎产物原样复制（可选）
```

**为什么几何与位置分开存**：`(w, h)` 和类别整场不变，读一次就够；
位置每帧都变，是动画的全部载荷。混在一起会让每帧的 I/O 翻倍。

### 3.2 `scene.json`

```json
{
  "format": "superplace-viz/1",
  "benchmark": "newblue1",
  "nodeCount": 330474,
  "core":      { "lx": 609,  "ly": 616,  "hx": 11783, "hy": 11776 },
  "chip":      { "lx": 0,    "ly": 0,    "hx": 12364, "hy": 12364 },
  "rowHeight": 12.0,
  "rows": 930,
  "flagBits":  { "macro": 1, "fixed": 2, "filler": 4, "ni": 8 },
  "hasMetrics": true,
  "frames": [
    { "file": "frames/f0000.bin", "stage": "input", "label": "input (newblue1.pl)" },
    { "file": "frames/f0001.bin", "stage": "init",  "label": "init (newblue1.init.pl)" },
    { "file": "frames/f0002.bin", "stage": "gp",    "label": "gp (newblue1.gp.pl)" }
  ]
}
```

> ⚠️ **`core` 与 `chip` 往往不一样，视野要按 `chip` 来 fit。**
> 真实设计的 I/O pad 大量位于 core **之外**（newblue1 的 337 个固定终端就在 core 外一圈）。
> 只按 core 适应窗口会把它们裁掉。

### 3.3 二进制文件布局

**全部小端、紧凑排列、无文件头**，直接 `read()` 进 `float` 数组即可，零解析开销。

| 文件 | 元素类型 | 长度 | 布局 |
| --- | --- | --- | --- |
| `geom.bin` | `float32` | `2 × nodeCount` | **交错**：`w₀ h₀ w₁ h₁ …` |
| `flags.bin` | `uint8` | `nodeCount` | `flags₀ flags₁ …` |
| `frames/*.bin` | `float32` | `2 × nodeCount` | **分块**：先 `x₀…x_{N-1}`，再 `y₀…y_{N-1}` |

节点下标在所有文件、所有帧中是同一套且恒定：第 `i` 个节点的宽是 `geom[2i]`、
标志是 `flags[i]`、在第 f 帧的中心是 `(frame.x[i], frame.y[i])`。

### 3.4 坐标约定（最容易出错的一条）

> **bundle 里的位置一律是【中心坐标】，不是左下角。**

BookShelf 的 `.pl` 用左下角，引擎内部用中心（算法侧的"铁律 2"），
bundle 跟随引擎用中心，换算只发生在 `make_viz.py` 里一处。
Y 轴向上为正，**翻转只应发生在最终投影那一步**。

### 3.5 节点类别与配色

`flags.bin` 的每个字节是位掩码，判定顺序必须固定：

```cpp
if (flags & 4) kind = Filler;        // F_FILLER
else if (flags & 2) kind = Fixed;    // F_FIXED（固定终端 / 已合法化的宏）
else if (flags & 1) kind = Macro;    // F_MACRO
else kind = Cell;
```

`F_NI`（bit 3）标记**零面积**的 I/O 引脚，`w = h = 0`，渲染时必须跳过。

配色与引擎的 PNG 输出（`src/plot/cimg_renderer.cpp`）一致，
这样界面和报告里的图看起来是同一个东西：

| 类别 | 颜色 | 默认可见 |
| --- | --- | --- |
| 标准单元 | 红 `#dc3c3c` | ✅ |
| 宏单元 | 橙 `#f59628` | ✅ |
| 固定终端 | 蓝 `#3d6edc` | ✅ |
| Filler | 绿 `#4fbe5a` | ❌（数量和单元同量级，默认开会糊掉） |

### 3.6 体积预算

每帧 = `nodeCount × 8` 字节。这是设计加载策略的唯一依据：

| 设计 | 节点数 | 单帧 | 40 帧动画 |
| --- | --- | --- | --- |
| 合成样本 | 8,080 | 65 KB | 2.7 MB |
| adaptec1 | 211k | 1.7 MB | 68 MB |
| newblue1 | 330k | 2.6 MB | 106 MB |
| bigblue4 | 2.18M | 17 MB | 700 MB |

**帧必须按需加载。** `BundleSource` 已实现按需读 + 最多缓存 24 帧的 LRU。
百万级设计要配合 `make_viz.py --max-frames` 抽样。

### 3.7 ⚠️ 同伴 clone 仓库后有哪些测试数据

**先说结论：一份都不会有，除了那个合成样本。**

`.gitignore` 里同时忽略了 `test_data/`、`benchmarks/`、`results/`
（分别是 125 MB / 2.7 GB / 1.2 GB，不适合进仓库）。所以新 clone 下来：

| 目录 | 在仓库里吗 | 后果 |
| --- | --- | --- |
| `gui/sample-data/synthetic` | ✅ **唯一自带的数据**（4.8 MB） | 查看器开箱即可运行 |
| `test_data/` | ❌ 被忽略 | **没有任何 `.aux`，实时模式跑不起来** |
| `benchmarks/` | ❌ 被忽略 | 无法生成真实数据的 bundle |
| `results/` | ❌ 被忽略 | 无法取各阶段 `.pl` 做多帧动画 |

因此测试数据分三档，**前两档完全不需要 benchmark**：

**第一档 · 合成样本（仓库自带，开箱可用）**

`gui/sample-data/synthetic`：14,681 个节点、40 帧。刻意覆盖了前端必须处理的
**全部节点形态**——标准单元、可移动宏、core 外的固定 I/O pad、零面积
`terminal_NI`、filler，以及"从中心一团逐步铺开"的收敛过程，外加一份形状合理的
`metrics.csv`。**功能正确性在它上面验完，真实数据基本不会有意外。**

**第二档 · 大规模合成样本（本地现生成，仍不需要 benchmark）**

性能和内存要用真实量级验证，合成生成器可以按需放大：

```bash
python3 scripts/make_viz.py --synthetic --cells 160000 --macros 236 \
                            --frames 6 --out /tmp/viz/big
#  -> 357,217 个节点（含 196,925 个 filler），6 帧，20 MB，耗时不到 1 秒
```

core 尺寸由单元总面积反推（目标利用率约 55%），所以放大节点数时 filler 数量与
密度都保持真实，不会出现"单元塞不下、空白为负、filler 归零"的失真样本。
实测这个 35.7 万节点的样本渲染中位 **1.55 ms/帧**，与真实 newblue1 的 1.80 ms 同量级。

**第三档 · 真实数据（必须由你线下提供）**

这一档绕不开。而且**同伴自己下载不到**——ISPD 的两个源都已失效
（UT Austin 返回 403，ispd.cc 对 GET 返回反爬挑战页，见
[04 §6.1](04-Benchmark%20调研与获取指南.md)）。两种给法：

| 方式 | 传输体积 | 同伴能做什么 |
| --- | --- | --- |
| **直接给打包好的 bundle**（推荐） | newblue1 三帧 **4.0 MB**（tar.gz） | 离线查看全部功能 |
| 给原始 benchmark 目录 | adaptec1 **5.4 MB**（tar.gz，解压后 40 MB） | 还能跑实时模式（需集成构建） |

推荐给 bundle：体积更小、不含同伴用不到的 `.nets`，而且**格式自带校验**——
`make_viz.py --verify` 能立刻判断传过去的东西是否完整。
只有要调试实时模式（缺口 #3）时才需要原始 `.aux`。

### 3.8 怎么生成 bundle

```bash
# 合成样本：不需要任何 benchmark 数据
python3 scripts/make_viz.py --synthetic --out gui/sample-data/synthetic

# 真实数据：需要 benchmark 原件 + 一次引擎运行的 results 目录
python3 scripts/make_viz.py --aux benchmarks/ispd2006/newblue1/newblue1.aux \
                            --result results/audit/newblue1 --out /tmp/viz/newblue1

# 校验 bundle 是否合规（格式争议由程序裁决，不靠人对文档）
python3 scripts/make_viz.py --verify gui/sample-data/synthetic
```

`make_viz.py` 是只读的——它读 BookShelf 原件与 `results/` 产物，不改引擎一行代码。
因此**引入前端这件事对算法侧的改动量是零**。

各档测试数据的来源与取舍见 §3.7。

## 4. 唯一的技术难点：几十万个矩形怎么画

[01 §7.4](01-架构设计与技术选型.md) 已有判断，这里给出已验证的实现要点。

**（1）绝不能一个单元一个对象。** 不要 `QGraphicsItem`、不要每单元一次 draw call。
33 万个对象光构造和场景索引就要几秒。

**（2）正确解法是 GPU 实例化。** 顶点缓冲里只放一个 0..1 的单位方片，
每个单元作为一个"实例"提供 `(cx, cy, w, h, kind)`，一次 `glDrawArraysInstanced`
画完全部。位置变了只需 `glBufferSubData` 覆盖实例缓冲（330k × 2 float = 2.6 MB）。

**（3）亚像素保护是正确性要求，不是优化。** 全芯片视角下标准单元只有零点几个像素，
原样画会碎成一片摩尔纹噪点，看起来像"布局是坏的"。顶点着色器里把屏幕空间边长
撑到至少 `uMinPx`：

```glsl
vec2 pxSize = aSize * uView.z;
vec2 size = aSize * max(vec2(1.0), uMinPx / max(pxSize, vec2(1e-6)));
```

顺带一个好性质：零面积的 `terminal_NI` 节点 `aSize = 0`，`0 × 任何数 = 0`，
退化四边形不产生任何片元，GPU 自己就消掉了——不需要额外的分支。

**（4）图层开关不要拆 draw call。** 直接把该类的 alpha 置 0，片元里 `discard`。
33 万实例下 GPU 完全不在乎这点无效片元，而按类拆分会让代码复杂不少。

**（5）进一步的 LOD（后续优化）。** 拉远到一定程度改画 bin 密度热力图而不是真实矩形，
KLayout 就是这么做的。密度场可以在查看器里由位置现算，不必加进 bundle。

## 5. 已实测的基线数据

下面的数字都是在本机实跑出来的，不是估计。改动渲染路径后可以用
`--bench` 复测，防止性能悄悄退化。

### 5.1 渲染性能

```bash
cd gui && GALLIUM_DRIVER=d3d12 ./build/superplace-viz /tmp/viz/newblue1 --bench 300
```

| 数据集 | 节点数 | 中位 | p95 | 折合 |
| --- | --- | --- | --- | --- |
| 合成样本 | 8,080 | 0.90 ms | 1.63 ms | 1112 fps |
| **newblue1** | **330,474** | **1.80 ms** | **3.14 ms** | **557 fps** |

视口 1600×980，**每帧都切换数据**（含位置上传），所以这是动画播放的真实负载。
`--bench` 会自动关掉 vsync，否则帧时间被钳在 16.7 ms，测不出余量还剩多少。

### ⛔ 不要修改

## 7. 快速上手

### 7.1 装依赖（一次性）

**独立模式（同伴日常开发，只需要这些）：**

```bash
sudo apt install -y libglfw3-dev libgl1-mesa-dev libx11-dev \
                    libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev
echo 'export GALLIUM_DRIVER=d3d12' >> ~/.bashrc && source ~/.bashrc
```

| 包 | 用途 |
| --- | --- |
| `libglfw3-dev` | 窗口与输入。CMake 走 `find_package(glfw3 3.3 REQUIRED)` |
| `libgl1-mesa-dev` | OpenGL 开发头文件（系统里只有运行时 `libGL.so.1` 是不够的） |
| `libx11-dev` 及四个 `libx*-dev` | GLFW 在 Linux 上的编译期依赖 |

**注意这里没有 FFTW / Eigen / libpng / OpenMP**——那些是算法侧的依赖，前端不需要。
ImGui 与 ImPlot 已 vendor，`nlohmann/json` 复用仓库根目录那份，都不必安装。

**集成模式额外需要**（只有要跑实时模式时才装；其实就是算法侧那套依赖，
如果主工程已经能构建，这些就都在了）：

```bash
sudo apt install -y pkgconf libpng-dev libeigen3-dev libfftw3-dev
```

`libsuperplace` 是静态库，它的传递依赖得由使用方链上，所以集成版才需要这些。

**可选小工具**：`--screenshot` 存的是 PPM，转 PNG 用
`python3 -c "from PIL import Image; Image.open('a.ppm').save('a.png')"`，
需要 `python3-pil`。

ImGui（docking 分支）与 ImPlot 已经 vendor 在 `gui/third_party/`，不需要联网。
这与项目既有做法一致（根目录 `third_party/` 里的 CImg 与 nlohmann 也是 vendor 的，
见 [01 §9.2](01-架构设计与技术选型.md)）。

> **为什么不用 CMake FetchContent 现拉**：本机到 GitHub 的 git clone 与 codeload
> 实测均不通（clone 100 秒零进展、tarball 90 秒 0 字节）。vendor 之后 clone 仓库
> 即可构建，比配置时现拉可靠得多。

### 7.1b 换一个 Linux 发行版 / 原生 Linux 能开发吗？

**能，而且比 WSL2 更省事。** 本工程没有任何 WSL 专属依赖，但有三处要按环境调整。

**（1）`GALLIUM_DRIVER=d3d12` 是 WSL2 专用，原生 Linux 上千万别设。**

它的作用是让 WSL2 里的 Mesa 走 Windows 的 D3D12 驱动。原生 Linux 上有真正的
GPU 驱动（i915 / amdgpu / nvidia），设了这个变量反而会去找不存在的 d3d12 后端。
**原生 Linux 什么都不用设**，`glxinfo -B` 里 `Accelerated: yes` 就行。

**（2）包名按发行版换。** 需要的东西只有三类：C++17 编译器、CMake ≥ 3.20、
GLFW ≥ 3.3 的开发包（它会带上 OpenGL 与 X11 的开发头文件）。

| 发行版 | 独立模式 | 集成模式额外 |
| --- | --- | --- |
| Debian / Ubuntu | `libglfw3-dev libgl1-mesa-dev libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev` | `pkgconf libpng-dev libeigen3-dev libfftw3-dev` |
| Fedora / RHEL | `glfw-devel mesa-libGL-devel libX11-devel libXrandr-devel libXinerama-devel libXcursor-devel libXi-devel` | `pkgconf libpng-devel eigen3-devel fftw-devel` |
| Arch | `glfw mesa libx11 libxrandr libxinerama libxcursor libxi` | `pkgconf libpng eigen fftw` |
| openSUSE | `glfw-devel Mesa-libGL-devel libX11-devel`（及四个 `libX*-devel`） | `pkgconf libpng16-devel eigen3-devel fftw3-devel` |

ImGui / ImPlot 已 vendor，`nlohmann/json` 用仓库里那份，都与发行版无关。

**（3）中文字体必须自己装一个。** 查找顺序是
`$SUPERPLACE_FONT` → `fc-list :lang=zh` → 一组常见路径（已覆盖
Debian/Fedora/Arch/openSUSE 的 Noto CJK 位置）。找不到会在 stderr 明确提示该装什么，
界面仍可用，只是中文显示为方块。

```bash
sudo apt install fonts-noto-cjk          # Debian/Ubuntu
sudo dnf install google-noto-sans-cjk-fonts   # Fedora
sudo pacman -S noto-fonts-cjk            # Arch
# 或者直接指定：export SUPERPLACE_FONT=/path/to/font.ttc
```

> **这一条本机踩过**：开发机的 Linux 侧一个中文字体都没装，界面上的中文全靠
> WSL 能读到的 `/mnt/c/Windows/Fonts/msyh.ttc` 撑着。换到原生 Linux 没有这条路径，
> 整个界面就会变成方块。现在的查找链就是为此加的。

**其余环境相关事项**

| 项 | 说明 |
| --- | --- |
| **Wayland 会话** | Ubuntu 的 `libglfw3` 是 **X11-only** 构建，Wayland 下走 XWayland，通常无感。要原生 Wayland 可装 `libglfw3-wayland`（Arch/Fedora 的 glfw 包一般已同时支持） |
| **OpenGL 版本** | 需要 **3.3 core**。任何 2010 年后的 GPU + 现代 Mesa 都满足 |
| **纯软件渲染**（服务器、虚拟机无 GPU） | `llvmpipe` 也能跑，但 33 万节点会很卡。**用小样本开发是完全可以的**：合成样本只有 1.4 万节点 |
| **远程 / 无显示器** | 需要 X11 转发或 VNC。`--bench` 与 `--screenshot` 仍需要一个 GL 上下文，**不能真正无头运行** |
| **macOS / Windows** | 代码本身可移植（GLFW + OpenGL 3.3 都跨平台），但 CMake 里的 `find_package(glfw3)` 与 `--verify` 脚本只在 Linux 上验证过。macOS 的 OpenGL 已废弃但 3.3 仍可用 |

### 7.2 构建并运行

```bash
cmake -S gui -B gui/build -DCMAKE_BUILD_TYPE=Release
cmake --build gui/build -j
cd gui && ./build/superplace-viz            # 默认加载 sample-data/synthetic
```

常用参数：

| 参数 | 用途 |
| --- | --- |
| `<bundle 目录>` | 加载指定 bundle |
| `--frame N` | 启动时跳到第 N 帧，`-1` = 最后一帧 |
| `--bench N` | 渲染 N 帧、报告耗时后退出（自动关 vsync），用于性能回归 |
| `--screenshot out.ppm` | 保存截图（PPM，可用 PIL 转 PNG） |
| `--shot-after 秒` | 正常跑 UI，到点自动截图并退出，用于脚本化出图 |

### 7.3 实时模式（可选）

前置条件：算法侧已构建出 `build/libsuperplace.a`，且 §7.1 的集成模式依赖已装。

```bash
cmake -S gui -B gui/build-int -DSUPERPLACE_ROOT=$PWD/build
```

### 8.3 四个已经踩过的坑（改渲染或布局时留意）

这几个都是花了实打实的时间定位出来的，写在这里省得再踩一次。

**（1）`PassthruCentralNode` 不能装窗口。** 它的语义是"中央节点**为空时**才透出背景"。
一旦把窗口停靠进中央节点，dockspace 会照常铺一层 `WindowBg`，把底下的 GL 内容
整个盖掉——现象是画布全白而 `glGetError()` 干净。**正确用法是让中央节点保持空**，
用 `DockBuilderGetCentralNode()` 取它的矩形，自己往那块区域画。
给窗口加 `NoBackground` 并不能解决。

**（2）dockspace 的 id 必须用 `DockSpaceOverViewport()` 的返回值。**
自己拼 `GetID("DockSpaceViewport_11111111")` 猜是错的，
`DockBuilderGetCentralNode()` 会返回 `nullptr`，画布静默地停在 1×1 不报任何错。

**（3）`fit` 不能在第一帧做。** 停靠布局在第一帧还没算好，此时画布只有几十像素，
照着它算出来的比例会小两个数量级（实测 0.002 px/unit，正确值约 0.3），
内容整个飞到视野外。要等画布尺寸稳定（`> 32 px`）再 fit。

**（4）GL 上下文就绪之前不能上传几何。** 集成版在 `run()` **之前**就注入数据源，
那时 `glLoad()` 还没跑、函数指针全是空的，直接段错误。
`App` 因此把上传推迟到 `uploadGeometry()`，由主循环在上下文就绪后触发——
接口不应该靠调用顺序来保证正确性。

### 9.2 第一批 · 热身（全部【A】，约 1–2 天）

熟悉代码结构用，每个都能独立交付。

#### T1 · 总览面板（读 `summary.json`）【A】

- **现状**：`make_viz.py` 已把 `summary.json` 复制进 bundle，`scene.json` 里也有
  `hasSummary` 标志，但**查看器里没有任何地方解析它**。
- **做什么**：在 `bundle_source.cpp` 里解析（nlohmann/json 已可用），
  经 `IPlacementSource` 暴露，在侧栏加一个「总览」分组展示。
- **展示哪些**：`gp_hpwl`、`gp_overflow`、`gp_movable_macros`、`gp_num_fillers`、
  `mlg_overlap_before/after`、`cgp_macros_moved`，以及 `durations_ms` 里各阶段耗时。
  字段含义见 [05 §9.3](05-开发执行规范.md)。
- **注意**：`summary.json` 的键会随算法演进增减，**不要写死键名列表后遇缺就崩**；
  按"有则显示"处理。`cgp_macros_moved` 非 0 是算法侧的 bug 信号，值得标红。
- **验收**：newblue1 的 bundle 上能看到完整总览；合成样本没有 `summary.json`，
  面板应显示"该 bundle 不含总览"而不是空白或崩溃。

#### T2 · 窗口 resize 后重新适应视野【A】

- **现状**：只能手动点「适应窗口」。拖动窗口边缘或改变面板比例后，
  视野不跟着变，内容会跑偏。
- **做法**：在 `drawCanvasPanel()` 里记住上一帧的 `canvasW_/H_`，
  变化超过阈值时**按比例调整 `cam_.scale`**，保持视野中心与可见范围不变。
- **坑**：不要简单地重新 `fit()`——那会丢掉用户已经缩放到的位置，体验很差。
  正确做法是保持 `cx/cy` 不动，`scale` 按短边比例缩放。
- **验收**：缩放到某个局部后拖动窗口大小，看到的区域不变、不变形。

#### T3 · 比例尺与坐标轴【A】

- **做什么**：画布左下角加一个随缩放自适应的比例尺（取 1/2/5 × 10ⁿ 的"好看"刻度），
  边缘加坐标刻度。
- **提示**：用 `ImGui::GetForegroundDrawList()` 画即可，中央节点里没有普通控件的位置。
  当前的坐标读数就是这么画的（`app.cpp` 的 `drawCanvasPanel`）。
- **验收**：从全芯片缩放到单个标准单元，比例尺始终显示合理的整数刻度。

### 9.3 第二批 · 核心能力（全部【A】，约 1–2 周）

**这一批是查看器真正的价值所在**，也是工作量主体。T4 是后面几项的前提，先做。

#### T4 · 空间索引 + 点选 + 检视面板【A】 ★ 最大的一块

- **为什么最重要**：它是 T7、T8、T10 的共同前提。没有点选，查看器只能"看个大概"，
  回答不了"这块密度为什么这么高""这个宏周围的单元被谁拉过去了"这类真问题
  （[01 §7.1](01-架构设计与技术选型.md) 说的交互式空间探索）。
- **技术要点**：**33 万节点不能线性扫**。建一个均匀网格索引即可：
  按 `chip` 划成 ~256×256 的桶，每桶存落入其中的节点下标（CSR 两趟构建，
  和算法侧 `PlaceDB::finalizeCSR` 同一套路）。点选时只查鼠标所在桶及其邻域。
- **坑一**：**位置每帧都变**，索引必须跟着重建。好在单帧重建是 O(N)，
  330k 节点约几毫秒；但**不要每帧都建**，只在切帧后第一次点选时懒重建。
- **坑二**：命中判定要用**真实矩形**而非渲染时被亚像素保护放大后的矩形，
  否则全芯片视角下点哪儿都能"命中"一片。
- **坑三**：重叠时该选谁。建议按"面积最小者优先"，否则点宏上面的标准单元永远选不中。
- **检视面板显示**：名字（依赖 T9）、下标、类别、宽高、中心坐标、所属 bin。
- **验收**：330k 节点上点选响应无可感延迟；选中项在画布上高亮；
  点空白处取消选中。

#### T5 · 收敛曲线改造【A】

- **现状**：横轴用的是**行序号**而非真实迭代数。因为 `metrics.csv` 的 `iter` 列
  在每个阶段都从 0 重数，直接当横轴会让曲线在阶段交界处折回去，看着像发散。
- **做什么**：按阶段拆成多条序列（mGP / FILLERONLY / cGP 各一条，不同颜色），
  横轴仍用累计序号但 tooltip 显示"阶段 + 阶段内迭代数"。
- **联动**：拖时间轴时曲线上出现游标；反过来点曲线能跳到对应帧。
  注意 bundle 的帧数远少于 metrics 的行数（帧是抽样的），要做一次映射。
- **验收**：newblue1 上三个阶段分色清晰；拖时间轴游标同步移动。

#### T6 · 密度热力图 + 远景 LOD【A】

- **做什么**：由当前帧位置**在查看器里现算** bin 密度（不必加进 bundle），
  画成热力图叠加；缩放比例小于某阈值时自动从"画真实矩形"切到"画热力图"。
- **为什么要 LOD**：全芯片视角下标准单元只有亚像素大小，现在靠亚像素保护硬撑成
  1.5 px，看到的其实是噪点而不是信息。热力图才是那个尺度上有意义的呈现方式。
  **KLayout 就是这么做的**（[01 §7.4](01-架构设计与技术选型.md)）。
- **算法**：累加每个节点与 bin 的重叠面积即可，不需要算法侧那套 local smoothing
  与密度缩放规则（那是给优化器用的，这里只是可视化）。**但要写清楚这一点**，
  否则日后会有人拿它和引擎的 τ 对不上而困惑。
- **验收**：热力图与同一帧的 PNG 在视觉上吻合；切换 LOD 时无跳变感。

#### T7 · 按属性着色【A】

- 可切换：按类别（现状）/ 按局部密度（复用 T6）/ 按相对上一帧的位移量 / 按 net 数。
- **实现**：给实例缓冲加一个 `float aValue`，片元里查颜色表。渲染路径改动很小。
- **验收**：切换即时生效；配色有图例与数值范围。

#### T8 · 两帧对比与位移矢量场【A】

- **做什么**：同时取两帧，用颜色（位移大小）或线段（位移方向）表示单元的移动。
- **用途**：一眼看出 mLG 把哪些宏挪了多远、cGP 把哪些单元重新拉回去了。
- **提示**：`BundleSource` 的 LRU 默认缓存 24 帧，取两帧不会触发反复 I/O。
- **验收**：MMS 数据上能清楚看出 mLG 前后宏的位移。

#### T9 · 补上 `names.txt` 的生成端【B】

- **现状**：`bundle_source.cpp` 写了读取逻辑，但 `make_viz.py` **根本不生成这个文件**，
  所以那段读取是**死代码**。
- **做什么**：在 `make_viz.py` 的 `Bundle` 里加 `write_names()`，每行一个节点名，
  顺序与 `geom.bin` 严格一致；`scene.json` 加 `hasNames` 标志。
- **体积**：newblue1 的 33 万个名字约 2.5 MB，**建议做成可选开关**（`--with-names`），
  默认不生成——只有要用检视面板（T4）时才需要。
- **坑**：filler 没有名字（它们是引擎生成的），要补占位串，否则行数对不上。
  `bundle_source.cpp` 已有"行数对不上就当没有"的保护，但那是兜底不是方案。
- **验收**：`--verify` 检查 `hasNames` 与实际行数一致；T4 的检视面板能显示真实名字。

#### T10 · 网表连接性进 bundle + 点选高亮【B】

- **前置**：T4（没有点选就谈不上高亮）。
- **契约扩展**：新增 `nets.bin`，CSR 两段式——`node2net_start`（`int32 × (N+1)`）
  与 `flat_node2net`（`int32 × 总 pin 数`），外加 `net2pin_start` / `flat_net2pin`。
  newblue1 约 8 MB，**必须做成可选**。
- **格式版本**：加了这个之后 `format` 升到 `superplace-viz/2`，但
  **`bundle_source.cpp` 的版本判断要保持向后兼容**——旧 bundle 仍应能加载。
- **渲染**：高亮可以在实例缓冲里加一个 `aHighlight` 标志位，或者单独用
  `ImDrawList` 画 net 的包围盒/星形连线。后者在 net 很多时更灵活。
- **验收**：点中一个单元后，它所在的全部 net 的其他引脚被高亮；
  超大 net（degree > 100）要能过滤掉，否则会糊满全屏。

### 9.5 第四批 · 涉及算法侧（【C】，**开发前必须与算法侧确认**）

> ⚠️ **这一批请不要直接动手。** 原因不是难，而是**错了不容易发现**：
> `live_source.cpp` 是整个工程里唯一 include 算法侧头文件的地方，
> 阶段语义搞错了界面照样能跑，只是显示的东西是错的。
> 而 T12 更是**必须改算法侧代码**才能做。
>
> 开工前请找算法侧的人一起过一遍方案，确认接口怎么加、谁来加。

#### T11 · 实时模式补齐四阶段【C】

- **现状**：`live_source.cpp:147` 写死 `engine.run(GpStage::kMGP)`，
  只跑第一个阶段，mLG / FILLERONLY / cGP 都没有。
- **参照实现**：`src/stages/gp_stage.cpp` 里已有完整的四阶段序列，照搬即可：
  `initializeFillers` → mGP → `legalizeMacros` → `scatterFillers` → FILLERONLY → cGP。
- **⚠️ 关键语义陷阱**：mLG 之后宏被置为 `F_FIXED`，它们的面积从"可移动电荷"
  变成"固定阻挡"，**必须重新构造 `EPlace` 对象**（构造函数里会重算全部静态密度项）。
  照抄 `gp_stage.cpp` 里"每个阶段各自新建 `EPlace`"的写法，不要图省事复用一个。
  这个坑在 [05 §5.6.2](05-开发执行规范.md) 与 M3 的实现注释里都有记录。
- **UI 侧**：时间轴要能区分阶段（帧的 `stage` 字段已经带了），
  mLG 是一次性跳变而非逐轮迭代，表现形式上要和 GP 阶段区分开。
- **验收**：MMS/newblue1 上四阶段依次执行；mLG 前后宏位置明显变化且之后不再动；
  最终 HPWL 与 CLI 跑同一设计的结果一致（这是正确性的硬判据）。

#### T12 · 实时模式的暂停 / 单步 / 停止【C】 ← **必须改算法侧**

- **暂停与单步**：可以不改算法侧。`EPlace::setIterCallback` 的回调跑在 worker
  线程里，在回调内部用条件变量阻塞即可实现暂停与单步。
- **⚠️ 但「停止」做不到**：**`EPlace::run()` 目前没有任何中断机制**
  （已核查 `src/gp/eplace.{h,cpp}`，没有 abort / cancel / 返回值中止路径），
  它是一个不可打断的阻塞循环。想中途停下只有两条路，**都要改算法侧**：
  1. 让 `IterCallback` 返回 `bool`，返回 false 时 `run()` 提前退出；
  2. 给 `EPlace` 加一个 `std::atomic<bool>* cancel` 令牌，每轮检查。
  第 1 种改动更小但会改变现有回调签名（`gp_stage.cpp` 的出图回调也要跟着改）。
- **所以**：这一项**必须先和算法侧谈定接口再动手**，不要在 gui 侧用
  "detach 线程然后不管它"之类的办法绕过去——那会在关窗时留下访问已析构 `PlaceDB`
  的悬垂引用。
- **验收**：跑到一半能暂停、单步前进、彻底停止并释放 worker；关窗不崩不泄漏。
