## 1. 三条约束，以及它们为什么不冲突

这套方案是从三条约束倒推出来的：

1. **与算法部分耦合要低。** `src/` 是迭代了几个月的东西，数值内核里全是符号与缩放的坑

   （05 §5.5.7 那几条"写反了会越跑越挤"的注释）。前端开发**不应该有能力**改坏它——
    不是靠约定，而是靠结构上做不到。
2. **前端要能脱离算法依赖独立测试。** 同伴不该为了看一眼界面，先把 FFTW、Eigen、

   libpng、OpenMP 装通再等几十秒编译。
3. **不对 GUI 的水平和质量作让步。** 包括 [01 §7.1](01-架构设计与技术选型.md)

   说的那个杀手锏——**看到单元在电场里从一团逐步散开的全过程**。

第三条曾经被理解为"必须边跑边看"，于是 GUI 进程里得跑着布局器，和前两条冲突。
初版的解法是把"链接算法"降级为一个可选的集成构建模式（`LiveSource`）。

**修订后的解法更简单：把"跑"和"看"彻底拆开。** CLI 跑布局时每隔 N 轮把全部节点位置
录成一帧；前端读这些帧，拖进度条就能看到全过程。看到的内容与"边跑边看"相同，
而前端从此**任何构建模式下都不链接算法库**。三条约束同时成立，结构也更简单。

## 2. 架构：单向依赖 + 一个文件契约

### 2.1 依赖方向是单向的，而且只经过文件

```
   算法侧（src/，根 CMake）                     前端（gui/，独立顶层 CMake）
  ┌──────────────────────────┐               ┌──────────────────────────────┐
  │ superplace-cli            │   写出         │ superplace-viz               │
  │   --frame-stride N  ──────┼──► viz bundle ─┼──► BundleSource ─► 渲染/面板  │
  │   (io/viz_writer)         │   （文件）      │   （只读文件，零算法依赖）     │
  └──────────────────────────┘               └──────────────────────────────┘
```

**根目录的** `CMakeLists.txt` **里没有任何一行提到** `gui`（可自行 `grep gui CMakeLists.txt` 验证），
`gui/` **也不链接** `libsuperplace`。两边唯一的交集是 bundle 这个目录格式（§3），
由 `scripts/make_viz.py --verify` 仲裁。

由此得到一个**结构性保证**：在 `gui/` 里做任何改动，都不可能让
`cmake --build build` 或 `ctest` 失败；算法侧怎么重构 `PlaceDB`，只要 bundle 格式不变，
前端一行都不用改。

### 2.2 只有一种构建模式

```bash
cmake -S gui -B gui/build && cmake --build gui/build -j
#   产出 superplace-viz：零算法依赖（ldd 里没有 FFTW / libpng / OpenMP / libsuperplace）
```

> 初版还有一个 `-DSUPERPLACE_ROOT=...` 的集成模式，产出内嵌引擎的 `superplace-gui`。
> 它连同 `live_source.{h,cpp}`、`main_gui.cpp`、`test_live_stages.cpp` 已在 PR #2 中删除
> （任务 [T16](#t16--删除实时模式代码a)）。

### 2.3 唯一的接缝：`IPlacementSource`

```cpp
class IPlacementSource {
public:
    virtual const SceneInfo&    scene()    const = 0;   // core/chip/计数，不变
    virtual const NodeGeometry& geometry() const = 0;   // w/h/flags，不变
    virtual const MetricsTable* metrics()  const = 0;
    virtual int  frameCount() const = 0;
    virtual bool frame(int index, FrameView& out) = 0;
};
```

现在只有一个实现 `BundleSource`。接口仍保留：它把"文件格式"和"UI 代码"隔开，
格式升级时只改 `bundle_source.cpp`。

> `FrameView` **的生命周期**：初版用裸指针指向 `BundleSource` 的帧缓存，缓存按 LRU 淘汰后
> 指针会悬垂，多帧 bundle 下热力图、点选会读到别的帧（[§8.3 坑（5）](#83-已经踩过的坑改渲染布局或数据层时留意)）。
> PR #2 已修复（任务 [T15](#t15--修复-frameview-悬垂指针a-阻塞-t14必须最先做)）：`FrameView` 改为持有
> `std::shared_ptr<const std::vector<float>>`，缓存淘汰不影响仍被持有的帧；另增 `frameInfo(i)`，
> 只取元数据、不读位置文件。

### 2.4 为什么取消实时模式（2026-11-03 决策）

实时模式让 GUI 在自己的进程里**再跑一遍完整布局**。问题不在于能不能跑通
（它在 newblue1 上与 CLI 的最终 HPWL 相对误差 3.5e-11），而在于它带来的长期成本：

| 问题 | 说明 |
| --- | --- |
| 流程有两份 | `live_source.cpp` 照着 `src/stages/gp_stage.cpp` 抄了一遍四阶段编排。抄错了界面照样跑、只是显示的不是 CLI 会产出的结果，所以每次改流程都要**对拍** |
| 配置有两份 | 实时模式用 C++ 默认构造的 `Config`，CLI 读 `configs/default.json`。两边目前碰巧一致，任何一方单独改都会**静默分叉** |
| 要改引擎 | "停止"需要 `EPlace::run()` 支持中途退出，而它没有任何中断机制（原 T12） |
| 要链接算法库 | 集成构建得装齐 FFTW / Eigen / libpng / OpenMP，与约束 2 相悖 |
| 资源争抢 | 内嵌引擎默认占满全部核；同时再跑一个 CLI，两边都会因 OpenMP 线程超订慢十几倍（实测 newblue1 从 25 s 变成 481 s） |

录制方案把这些问题一次性消掉：流程只有 CLI 一份，配置只有一份，不需要引擎中断，
前端永不链接算法库。

**失去的东西**：进程内的暂停 / 单步（回放里拖进度条、逐帧前后跳可以覆盖观察需求），
以及"边跑边调参数"（本项目没有这个需求）。若将来真要"边跑边看"，CLI 本来就是
边跑边写 bundle（每录一帧都会原子地重写 `scene.json`），前端轮询目录即可，
仍然不需要链接算法库。

### 2.5 前端启动布局与 GDSII 导出（2026-11-09 决策）

> **总原则：前端只为最终答辩演示服务。** 只保证事先选定的**演示路径**稳定走通；
> 不要求能打开任意设计，不要求在任意环境下都能跑通全流程，也不追求出错后的自动恢复。
> 凡是只为「任意输入、可配置、出错恢复」准备的功能，一律砍掉或写死。**评估新需求时先问：演示时看得到吗？**

**演示路径**：

1. 不带参数启动，前端是空白状态：画布灰色、不能操作，收敛曲线空白，右栏只显示「数据源」。
2. 在右栏「数据源」的**下拉框**里选设计。下拉框只有固定几项（§3.10），不弹文件对话框，也不扫描目录。
3. 选「newblue1」后，在底部「终端」标签页输入 `place`，前端以**子进程**运行 `superplace-cli` 现场布局（本机约 53 秒）。
   终端只显示开始、阶段切换、完成或失败。
4. 完成后自动加载新结果，接着演示回放、点选检视、net 高亮、着色与 GDSII 导出。
5. **兜底**：现场布局出问题时，直接在下拉框里选事先录好的 newblue1 继续演示。

**为什么不违背「前端零依赖」**：前端仍然不链接任何算法库，只是**运行** `superplace-cli` 这个可执行文件，
数据仍然只通过文件交换（与 §2.1 一致）。这和 2026-11-03 取消的实时模式（§2.4）有本质区别：
实时模式是把引擎编进前端进程、逐轮共享内存；这里两边隔着进程边界，CLI 照常把录制结果写到磁盘，前端在它结束后再读。

**与最初定位的关系**：[01 §7.1](01-架构设计与技术选型.md) 写过「GUI 是观察器，不是图形化启动器」，
担心的是「给参数配一堆输入框加一个运行按钮」。本决策仍然遵守这条底线：前端**不提供任何布局参数**，
一律用 `configs/default.json`。前端范围以本文为准。

**独立性**：查看功能照旧零依赖，同伴在没有算法依赖的机器上照样能开发和测试（用合成样例）。
现场布局只在演示机器上需要，那里已经构建好 `build/superplace-cli`。

**明确不做**：

| 不做 | 原因 |
| --- | --- |
| 文件对话框、扫描本地设计目录、打开任意设计 | 演示只用固定的几项，下拉框写死即可 |
| 布局参数（步长、线程数、初始化方法等） | 演示用默认配置；也避免退化成「参数表单」 |
| 出错恢复（旧结果备份与回滚、关窗确认等） | 现场布局写到单独目录，永远不覆盖录好的结果（§3.10），失败了切回录好的那份即可 |
| 真正的 shell（任意命令、伪终端、颜色控制码） | 终端只认 `place` / `stop` / `help` / `clear` 四条命令 |
| 运行中实时显示布局画面 | 即 §2.4 取消的实时模式。运行中只显示进度文字，结束后一次性加载 |
| GDSII 导入；CLI 侧的 GDSII 导出 | 演示不需要 |
| GDS 的 site row 层与 filler 层 | 录制结果里没有这两类数据，补数据不值得（原 T35） |
| 左侧面板 | 新入口都放进右栏「数据源」 |

## 3. 数据契约 `superplace-viz/1`

前端读的唯一文件格式。它同时也是**框架无关的资产**——将来若要换 Qt 或做 Web 版，
契约可以原样复用，重写的只是渲染与 UI 那层。

有两个生产者，产出同一种格式：

| 生产者                                                        | 用途                               | 帧数                              | 节点顺序          |
| ---------------------------------------------------------- | -------------------------------- | ------------------------------- | ------------- |
| `superplace-cli --frame-stride N`（`src/io/viz_writer.cpp`） | **真实设计的回放**，主力                   | 每 N 轮 GP 一帧（newblue1、N=10：62 帧） | 引擎内存顺序        |
| `scripts/make_viz.py`                                      | 合成样本；给旧的 `results/` 补一个静态 bundle | 每阶段结束一帧（3~4 帧）                  | `.nodes` 文件顺序 |

### 3.1 目录结构

```
<bundle>/
├── scene.json        元数据（小、人可读，唯一的 JSON）
├── geom.bin          静态几何：每节点 (w, h)
├── flags.bin         静态类别：每节点 1 字节标志位
├── frames/
│   ├── f0000.bin     位置快照：x[N] 紧接 y[N]
│   └── …
├── names.txt         每行一个节点名，供检视面板用（CLI 录制必带；合成样本不带）
├── nets/             网表（可选扩展，见 §3.9；T10 用）
├── metrics.csv       引擎产物原样复制（可选）
└── summary.json      引擎产物原样复制（可选）
```

**为什么几何与位置分开存**：`(w, h)` 和类别整场不变，读一次就够；
位置每帧都变，是动画的全部载荷。混在一起会让每帧的 I/O 翻倍。

```json
  "frameStride": 10, "hasNames": true, "hasMetrics": true, "hasSummary": true,
  "frames": [
    { "file": "frames/f0000.bin", "stage": "input", "iter": -1,  "t": 0,   "breakBefore": false, "label": "输入（.pl 初始位置）" },
    { "file": "frames/f0001.bin", "stage": "init",  "iter": -1,  "t": 0,   "breakBefore": true,  "label": "init 结束" },
    { "file": "frames/f0002.bin", "stage": "mGP",   "iter": 0,   "t": 0,   "breakBefore": false, "label": "mGP iter 0" },
    …
    { "file": "frames/f0050.bin", "stage": "mGP",   "iter": 476, "t": 476, "breakBefore": false, "label": "mGP 结束" },
    { "file": "frames/f0051.bin", "stage": "mLG",   "iter": -1,  "t": 476, "breakBefore": true,  "label": "mLG 宏合法化（宏跳到合法位置）" },
    { "file": "frames/f0052.bin", "stage": "cGP",   "iter": 10,  "t": 506, "breakBefore": false, "label": "cGP iter 10" },
    …
    { "file": "frames/f0061.bin", "stage": "cGP",   "iter": 95,  "t": 591, "breakBefore": false, "label": "cGP 结束" }
  ]
}
```

帧条目里的 `iter` / `t` / `breakBefore` 是**可选字段**（`make_viz.py` 产出的 bundle 不带），
前端缺省时按"帧序号均匀分布、处处可插值"处理。字段含义：

| 字段            | 含义                                                      | 前端怎么用                                                                               |
| ------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `stage`       | `input` / `init` / `mGP` / `mLG` / `FILLERONLY` / `cGP` | 进度条按阶段分色；与 `metrics.csv` 的 `stage` 列同名，可直接关联                                        |
| `iter`        | 阶段内迭代号；`-1` **表示阶段里程碑**而非某一轮                            | `(stage, iter)` 精确对应 `metrics.csv` 的一行，T5 的帧↔行映射无需再猜                                |
| `t`           | **全局进度**：跨 mGP / FILLERONLY / cGP 累计的迭代数，**单调不减**       | 回放的时间轴。按 t 匀速播放 = 按迭代速率播放；相邻两帧 t 相等表示瞬时切换                                           |
| `breakBefore` | 与上一帧之间是**跳变**                                           | **不得插值**，必须硬切。目前有三种来源：init（二次布局的迭代没录）、mLG（宏一次性跳到合法位置）、GP 子阶段因 τ 停滞而**回退到更早某一轮**的收尾帧 |

录制时有两条规则，前端看到的帧序列会因此"缺"一些帧，这是预期行为：

- **与上一帧逐位相同的帧不写。** 例如 FILLERONLY 阶段只动 filler，真实节点纹丝不动，
这 20 轮全部被跳过（但它们仍计入 `t`，所以 t 会从 476 跳到 496）；
cGP 第 0 轮回调时位置还是 mLG 的结果，也被跳过。
- **逐轮帧是 Nesterov 的前瞻点**，与 `metrics.csv` 同一行的 HPWL/τ 对应同一个点。
每个 GP 子阶段结束时另打一个"结束"帧，它就是写进 `.pl` 的交付布局（newblue4 上逐节点
比对 64.6 万个节点，偏差为 0）。三种情形：
  - **达标收敛**：交付的就是最后一轮的前瞻点，"结束"帧与最后一个逐轮帧相同，被当作重复帧跳过
  （所以 adaptec1 的末帧标签是 `mGP iter 300` 而不是 `mGP 结束`，这是正常的）；
  - **耗尽迭代上限**：交付的是当前解，与最后一轮只差一步动量，正常插值；
  - **τ 停滞回退**：交付的是更早某一轮的快照，"结束"帧标 `breakBefore`，标签写明回退到第几轮
  （newblue4：第 645 轮判定停滞、回退到第 431 轮，末帧相对前一帧平均跳 114 个单位）。

> ⚠️ `core` **与** `chip` **往往不一样，视野要按** `chip` **来 fit。**
> 真实设计的 I/O pad 大量位于 core **之外**（newblue1 的 337 个固定终端就在 core 外一圈）。
> 只按 core 适应窗口会把它们裁掉。

### 3.3 二进制文件布局

**全部小端、紧凑排列、无文件头**，直接 `read()` 进 `float` 数组即可，零解析开销。

| 文件 | 元素类型 | 长度 | 布局 |
| --- | --- | --- | --- |
| `geom.bin` | `float32` | `2 × nodeCount` | **交错**：`w₀ h₀ w₁ h₁ …` |
| `flags.bin` | `uint8` | `nodeCount` | `flags₀ flags₁ …` |
| `frames/*.bin` | `float32` | `2 × nodeCount` | **分块**：先 `x₀…x_{N-1}`，再 `y₀…y_{N-1}` |

节点下标在所有文件、所有帧中是同一套且恒定：第 `i` 个节点的宽是 `geom[2i]`、
标志是 `flags[i]`、在第 f 帧的中心是 `(frame.x[i], frame.y[i])`。

> ⚠️ **不同生产者的节点顺序不同，绝对不能混用。** 引擎读入时 `partitionNodes()` 会把节点
> 重排成"可移动在前、固定在后"，且不保留旧序映射，所以 CLI 录制的 bundle 用的是引擎内存顺序；
> `make_viz.py` 用的是 `.nodes` 文件顺序。拿一个来源的 `geom.bin` 配另一个来源的帧，
> 画面会完全错乱，而且 `--verify` 查不出来（尺寸都对得上）。

> 帧里**只有真实节点**，不含 filler（filler 是引擎在 GP 阶段临时插入的，个数随 τ 变化，
> 且数量与单元同量级——newblue1 若带上 filler，每帧体积翻倍）。

### 3.4 坐标约定（最容易出错的一条）

> **bundle 里的位置一律是【中心坐标】，不是左下角。**

BookShelf 的 `.pl` 用左下角，引擎内部用中心（算法侧的"铁律 2"），
bundle 跟随引擎用中心。CLI 录制直接写引擎内存里的中心坐标，不做任何换算；
`make_viz.py` 读 `.pl` 时在脚本里换算一次。
Y 轴向上为正，**翻转只应发生在最终投影那一步**。

### 3.5 节点类别与配色

`flags.bin` 的每个字节是位掩码，判定顺序必须固定：

```cpp
if (flags & 4) kind = Filler;        // F_FILLER
else if (flags & 2) kind = Fixed;    // F_FIXED（固定终端 / 已合法化的宏）
else if (flags & 1) kind = Macro;    // F_MACRO
else kind = Cell;
```

`F_NI`（bit 3）标记**零面积**的 I/O 引脚，`w = h = 0`，渲染时必须跳过。

配色与引擎的 PNG 输出（`src/plot/cimg_renderer.cpp`）一致，
这样界面和报告里的图看起来是同一个东西：

| 类别 | 颜色 | 默认可见 |
| --- | --- | --- |
| 标准单元 | 红 `#dc3c3c` | ✅ |
| 宏单元 | 橙 `#f59628` | ✅ |
| 固定终端 | 蓝 `#3d6edc` | ✅ |
| Filler | 绿 `#4fbe5a` | ❌（数量和单元同量级，默认开会糊掉） |

### 3.6 体积预算

每帧 = `nodeCount × 8` 字节。这是设计加载策略的唯一依据：

| 设计 | 节点数 | 单帧 | 录制（每 10 轮一帧） | 合计 |
| --- | --- | --- | --- | --- |
| 合成样本 | 14,681 | 117 KB | 40 帧 | 5.2 MB（含网表 0.4 MB） |
| MMS adaptec1 | 211k | 1.7 MB | 约 51 帧（估） | 约 86 MB |
| **newblue1** | **330k** | **2.6 MB** | **62 帧（实测）** | **162 MB（tar.gz 后 126 MB）** |
| bigblue4 | 2.18M | 17 MB | 约 125 帧（估） | 约 2.2 GB |

坐标是 float32，几乎压不动（newblue1 只压到 78%）。所以：

- **帧必须按需加载**，不能开场全读。`BundleSource` 是按需读 + 最多缓存 24 帧的 LRU；
（悬垂指针问题已由 [T15](#t15--修复-frameview-悬垂指针a-阻塞-t14必须最先做) 修复）。
- 回放时**预读**后面几帧（[T17](#t17--回放预读a)，已实现）：newblue1 每帧 2.6 MB 还好，bigblue4 每帧 17 MB，同步读会卡顿。
- 百万节点级的设计录制时用更大的步长（如 `--frame-stride 25`）。按位移自适应取帧、
坐标量化为 16 位整数等压缩手段是后续选项，**目前不做**。

### 3.9 可选扩展：网表 `nets/`（2026-11-04 约定，供 T10 使用）

用途：点选一个单元后高亮它所在的全部 net（T10）、「按 net 数」着色（T7 里目前禁用的那一项）、
检视面板显示 net 名与度数。

**三条原则**

1. **纯增量、可选**。`format` 仍是 `superplace-viz/1`；`scene.json` 里**没有** `nets` **键就是没有网表**，

   前端照常工作，相关功能禁用并注明原因。旧 bundle 不需要重录，旧版前端遇到新 bundle 也只是忽略这个键。
2. **原样写出引擎的 CSR**。引脚下标就是引擎内存里的引脚下标，节点下标就是 bundle 的节点下标

   （与 `geom.bin`、帧文件同一套，见 §3.3）。写出器不重排、不换算，和帧文件一样直接写 `PlaceDB` 的数组。
3. **只含真实节点**。filler 没有引脚，`pin_node` 的取值范围是 `[0, nodeCount)`。

**文件**（全部小端、紧凑、无文件头，与 §3.3 相同）

| 文件 | 元素类型 | 长度 | 内容 | 对应 `PlaceDB` 字段 |
| --- | --- | --- | --- | --- |
| `nets/net_start.bin` | `int32` | `netCount + 1` | net k 的引脚是 `net_pins[net_start[k] .. net_start[k+1])` | `net2pin_start` |
| `nets/net_pins.bin` | `int32` | `pinCount` | 按 net 分组的引脚下标 | `flat_net2pin` |
| `nets/pin_node.bin` | `int32` | `pinCount` | 引脚 p 所属节点 | `pin2node` |
| `nets/pin_offset.bin` | `float32` | `2 × pinCount` | **交错** `dx₀ dy₀ dx₁ dy₁ …`，相对所属节点**中心**，是**第 0 帧**时的值 | `pin_offset_x/y` |
| `nets/pin_offset_fNNNN.bin` | 12 字节记录 | 见下 | 引脚偏移的稀疏更新 | — |
| `nets/net_names.txt` | 文本 | `netCount` 行 | 每行一个 net 名 | `net_name` |
| `nets/net_weight.bin` | `float32` | `netCount` | net 权重；**只有存在不等于 1 的权重时才写** | `net_weight` |

`scene.json` **新增的键**（newblue1 的实际规模）：

```json
"nets": {
  "netCount": 338901,
  "pinCount": 1244342,
  "hasNames": true,
  "hasWeights": false,
  "offsetUpdates": [
    { "frame": 30, "file": "nets/pin_offset_f0030.bin", "count": 18 }
  ]
}
```

（规模取自 newblue1，`offsetUpdates` 取自合成样本：newblue1 实际为空数组，原因见下。）

**引脚坐标**：第 f 帧引脚 p 的绝对坐标 =
`(x_f[pin_node[p]] + dx_f(p), y_f[pin_node[p]] + dy_f(p))`，其中 `dx_f, dy_f` 是第 f 帧生效的偏移（见下）。

**为什么需要偏移更新**：mLG 的宏退火会把宏**左右翻转**，翻转时直接把该宏全部引脚的 x 偏移取反
（`src/lg/macro_sa.cpp` 写回段）。所以引脚偏移不是整场不变的——不处理的话，mLG 之后被翻转的宏，
其引脚位置会画在镜像的一侧。规则如下：

- 更新文件由 12 字节的记录组成，`struct { int32 pin; float32 dx; float32 dy; }`，无填充；
`dx, dy` 是**新的绝对偏移**，不是增量。记录数 = 文件字节数 / 12 = `count`。
- `frame` 是帧数组的下标：从这一帧（含）起，这些引脚改用新偏移。多次更新按 `frame` 升序**累积**生效：
第 f 帧的偏移 = `pin_offset.bin` 依次叠加所有 `frame ≤ f` 的更新。
- 写出器保证：**带偏移更新的帧一定是** `breakBefore = true`（mLG 帧本来就是）。
所以插值永远不会跨过一次偏移变化，插值时用区间起点 `lo` 帧的偏移即可。
- 写出器在每次 `append()` 时比较当前偏移与上次写出的快照；偏移有变化时，**即使位置与上一帧逐位相同，这一帧也不跳过**。
- **真实设计里翻转很少见**：翻转只占退火随机动作的十分之一，而且只有让代价变好才会被保留。
2026-11-04 录制的 newblue1（64 个宏）与 MMS adaptec1（63 个宏）都没有宏被翻转（最终 `.pl` 里没有
`FN` / `FS`），所以 `offsetUpdates` 是空数组。**前端测试这条路径请用合成样本**：它在第 30 帧（标为断点）
翻转了 3 个宏，共 18 个引脚。

**前端自己派生、不进文件的数据**：节点到引脚的反查（`node → pins`）和引脚到 net 的反查（`pin → net`），
加载时用两趟计数在 O(P) 时间内建好（做法同 `PlaceDB::finalizeCSR`）。不存它们，是为了把体积压到一半、
也让写出器保持「原样写数组」。

**度数与过滤**：度数为 0 或 1 的 net 原样保留，由前端决定是否显示。高亮时默认跳过度数 > 100 的 net
（时钟、复位这类大 net 会连满全屏），阈值可调。「按 net 数着色」的值定义为**该节点连接的不同 net 个数**
（同一节点的多个引脚落在同一 net 上只算一次）。

**体积**：

| 设计 | net 数 | 引脚数 | `nets/` 合计（不含名字） | 对比帧文件合计 |
| --- | --- | --- | --- | --- |
| newblue1 | 338,901 | 1,244,342 | 21 MB（实测；加 net 名共 23 MB） | 162 MB |
| bigblue4 | 约 223 万 | 约 890 万（估） | 约 150 MB（估） | 约 2.2 GB |

newblue1 的 net 名另外约几 MB。百万引脚级别的设计，前端应在**首次用到网表时**再加载，不要拖慢打开速度。

`--verify` **增加的检查**（任何一条不满足即报错）：

- 四个必需文件的字节数分别等于 `4(M+1)`、`4P`、`4P`、`8P`；
- `net_start[0] = 0`、单调不减、`net_start[M] = P`；
- `net_pins` 恰好是 `[0, P)` 的一个排列（每个引脚出现且只出现一次）；
- `pin_node` 全部落在 `[0, nodeCount)`；偏移全部是有限值；
- 每个更新文件字节数 = `12 × count`，引脚下标在范围内，`frame` 严格升序且对应的帧 `breakBefore = true`；
- `hasNames` 时 `net_names.txt` 恰为 M 行；`hasWeights` 时 `net_weight.bin` 为 `4M` 字节。

**生产者**：

| 生产者 | 是否写网表 | 说明 |
| --- | --- | --- |

## 4. 唯一的技术难点：几十万个矩形怎么画

[01 §7.4](01-架构设计与技术选型.md) 已有判断，这里给出已验证的实现要点。

**（1）绝不能一个单元一个对象。** 不要 `QGraphicsItem`、不要每单元一次 draw call。
33 万个对象光构造和场景索引就要几秒。

**（2）正确解法是 GPU 实例化。** 顶点缓冲里只放一个 0..1 的单位方片，
每个单元作为一个"实例"提供 `(cx, cy, w, h, kind)`，一次 `glDrawArraysInstanced`
画完全部。位置变了只需 `glBufferSubData` 覆盖实例缓冲（330k × 2 float = 2.6 MB）。

**（3）亚像素保护是正确性要求，不是优化。** 全芯片视角下标准单元只有零点几个像素，
原样画会碎成一片摩尔纹噪点，看起来像"布局是坏的"。顶点着色器里把屏幕空间边长
撑到至少 `uMinPx`：

```glsl
vec2 pxSize = aSize * uView.z;
vec2 size = aSize * max(vec2(1.0), uMinPx / max(pxSize, vec2(1e-6)));
```

顺带一个好性质：零面积的 `terminal_NI` 节点 `aSize = 0`，`0 × 任何数 = 0`，
退化四边形不产生任何片元，GPU 自己就消掉了——不需要额外的分支。

**（4）图层开关不要拆 draw call。** 直接把该类的 alpha 置 0，片元里 `discard`。
33 万实例下 GPU 完全不在乎这点无效片元，而按类拆分会让代码复杂不少。

**（5）进一步的 LOD（后续优化）。** 拉远到一定程度改画 bin 密度热力图而不是真实矩形，
KLayout 就是这么做的。密度场可以在查看器里由位置现算，不必加进 bundle。

## 7. 快速上手

### 7.1 装依赖（一次性）

**独立模式（同伴日常开发，只需要这些）：**

```bash
sudo apt install -y libglfw3-dev libgl1-mesa-dev libx11-dev \
                    libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev
echo 'export GALLIUM_DRIVER=d3d12' >> ~/.bashrc && source ~/.bashrc
```

| 包 | 用途 |
| --- | --- |
| `libglfw3-dev` | 窗口与输入。CMake 走 `find_package(glfw3 3.3 REQUIRED)` |
| `libgl1-mesa-dev` | OpenGL 开发头文件（系统里只有运行时 `libGL.so.1` 是不够的） |
| `libx11-dev` 及四个 `libx*-dev` | GLFW 在 Linux 上的编译期依赖 |

**注意这里没有 FFTW / Eigen / libpng / OpenMP**——那些是算法侧的依赖，前端不需要。
ImGui 与 ImPlot 已 vendor，`nlohmann/json` 复用仓库根目录那份，都不必安装。

> 初版这里还有一段"集成模式额外需要 FFTW / Eigen / libpng"，实时模式取消后已不再需要。

**可选小工具**：`--screenshot` 存的是 PPM，转 PNG 用
`python3 -c "from PIL import Image; Image.open('a.ppm').save('a.png')"`，
需要 `python3-pil`。

ImGui（docking 分支）与 ImPlot 已经 vendor 在 `gui/third_party/`，不需要联网。
这与项目既有做法一致（根目录 `third_party/` 里的 CImg 与 nlohmann 也是 vendor 的，
见 [01 §9.2](01-架构设计与技术选型.md)）。

> **为什么不用 CMake FetchContent 现拉**：本机到 GitHub 的 git clone 与 codeload
> 实测均不通（clone 100 秒零进展、tarball 90 秒 0 字节）。vendor 之后 clone 仓库
> 即可构建，比配置时现拉可靠得多。

### 7.1b 换一个 Linux 发行版 / 原生 Linux 能开发吗？

**能，而且比 WSL2 更省事。** 本工程没有任何 WSL 专属依赖，但有三处要按环境调整。

**（1）**`GALLIUM_DRIVER=d3d12` **是 WSL2 专用，原生 Linux 上千万别设。**

它的作用是让 WSL2 里的 Mesa 走 Windows 的 D3D12 驱动。原生 Linux 上有真正的
GPU 驱动（i915 / amdgpu / nvidia），设了这个变量反而会去找不存在的 d3d12 后端。
**原生 Linux 什么都不用设**，`glxinfo -B` 里 `Accelerated: yes` 就行。

**（2）包名按发行版换。** 需要的东西只有三类：C++17 编译器、CMake ≥ 3.20、
GLFW ≥ 3.3 的开发包（它会带上 OpenGL 与 X11 的开发头文件）。

| 发行版 | 需要的包 |
| --- | --- |
| Debian / Ubuntu | `libglfw3-dev libgl1-mesa-dev libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev` |
| Fedora / RHEL | `glfw-devel mesa-libGL-devel libX11-devel libXrandr-devel libXinerama-devel libXcursor-devel libXi-devel` |
| Arch | `glfw mesa libx11 libxrandr libxinerama libxcursor libxi` |
| openSUSE | `glfw-devel Mesa-libGL-devel libX11-devel`（及四个 `libX*-devel`） |

ImGui / ImPlot 已 vendor，`nlohmann/json` 用仓库里那份，都与发行版无关。

**（3）中文字体必须自己装一个。** 查找顺序是
`$SUPERPLACE_FONT` → `fc-list :lang=zh` → 一组常见路径（已覆盖
Debian/Fedora/Arch/openSUSE 的 Noto CJK 位置）。找不到会在 stderr 明确提示该装什么，
界面仍可用，只是中文显示为方块。

```bash
sudo apt install fonts-noto-cjk          # Debian/Ubuntu
sudo dnf install google-noto-sans-cjk-fonts   # Fedora
sudo pacman -S noto-fonts-cjk            # Arch
# 或者直接指定：export SUPERPLACE_FONT=/path/to/font.ttc
```

> **这一条本机踩过**：开发机的 Linux 侧一个中文字体都没装，界面上的中文全靠
> WSL 能读到的 `/mnt/c/Windows/Fonts/msyh.ttc` 撑着。换到原生 Linux 没有这条路径，
> 整个界面就会变成方块。现在的查找链就是为此加的。

**其余环境相关事项**

| 项 | 说明 |
| --- | --- |
| **Wayland 会话** | Ubuntu 的 `libglfw3` 是 **X11-only** 构建，Wayland 下走 XWayland，通常无感。要原生 Wayland 可装 `libglfw3-wayland`（Arch/Fedora 的 glfw 包一般已同时支持） |
| **OpenGL 版本** | 需要 **3.3 core**。任何 2010 年后的 GPU + 现代 Mesa 都满足 |
| **纯软件渲染**（服务器、虚拟机无 GPU） | `llvmpipe` 也能跑，但 33 万节点会很卡。**用小样本开发是完全可以的**：合成样本只有 1.4 万节点 |
| **远程 / 无显示器** | 需要 X11 转发或 VNC。`--bench` 与 `--screenshot` 仍需要一个 GL 上下文，**不能真正无头运行** |
| **macOS / Windows** | 代码本身可移植（GLFW + OpenGL 3.3 都跨平台），但 CMake 里的 `find_package(glfw3)` 与 `--verify` 脚本只在 Linux 上验证过。macOS 的 OpenGL 已废弃但 3.3 仍可用 |

### 8.3 已经踩过的坑（改渲染、布局或数据层时留意）

这几个都是花了实打实的时间定位出来的，写在这里省得再踩一次。

**（1）**`PassthruCentralNode` **不能装窗口。** 它的语义是"中央节点**为空时**才透出背景"。
一旦把窗口停靠进中央节点，dockspace 会照常铺一层 `WindowBg`，把底下的 GL 内容
整个盖掉——现象是画布全白而 `glGetError()` 干净。**正确用法是让中央节点保持空**，
用 `DockBuilderGetCentralNode()` 取它的矩形，自己往那块区域画。
给窗口加 `NoBackground` 并不能解决。

**（2）dockspace 的 id 必须用** `DockSpaceOverViewport()` **的返回值。**
自己拼 `GetID("DockSpaceViewport_11111111")` 猜是错的，
`DockBuilderGetCentralNode()` 会返回 `nullptr`，画布静默地停在 1×1 不报任何错。

**（3）**`fit` **不能在第一帧做。** 停靠布局在第一帧还没算好，此时画布只有几十像素，
照着它算出来的比例会小两个数量级（实测 0.002 px/unit，正确值约 0.3），
内容整个飞到视野外。要等画布尺寸稳定（`> 32 px`）再 fit。

**（4）GL 上下文就绪之前不能上传几何。** 当时的集成版在 `run()` **之前**就注入数据源，
那时 `glLoad()` 还没跑、函数指针全是空的，直接段错误。
`App` 因此把上传推迟到 `uploadGeometry()`，由主循环在上下文就绪后触发——
接口不应该靠调用顺序来保证正确性。

**（5）**`FrameView` **里的指针在下一次** `frame()` **之后可能失效。**（已由 PR #2 / T15 修复，记录在此供以后改数据层时参考） 它用裸指针指向
`BundleSource` 的帧缓存，而缓存按 LRU 只留 24 帧。若先拿到第 N 帧的 `FrameView`，
之后又有代码取了足够多的其他帧，第 N 帧的缓冲区会被释放，指针悬垂，读到的是
**恰好复用了那块内存的另一帧**——不报错、不崩溃（大多数时候），只是画错。

这是 2026-11-03 用 CLI 录制的 62 帧 newblue1 bundle 验证 PR #1 时发现的：
`--frame 3 / 20 / 30 / 61` 四次启动，热力图实际画的分别是第 53 / 45 / 49 / 49 帧
（在临时副本里打印 `cur_.x` 指向的数值，与帧文件逐一比对确认）。触发链是：

1. `gotoFrame(N)` 把第 N 帧读进缓存，`cur_` 记下指针；矩形渲染**立刻**用它上传了 GPU，所以矩形是对的；
2. 收敛曲线面板首次绘制时，T5 为了拿每帧的 `stage/label`，**对全部 62 帧调用了** `frame()`——

   这会把每一帧的位置数据（每帧 2.6 MB）都读进来，第 N 帧最先被挤出缓存；
3. 热力图、点选索引、属性着色都是**懒计算**，事后按 `cur_.x` 去读，读到的已是别的帧。

旧 bundle 只有 3~4 帧，远少于缓存容量，从不淘汰，所以 PR 的 1400 多项测试都没覆盖到。
**责任一半在初版接口**：注释把"直接指向缓存"当优点写，却没写明失效条件。修法见 T15。

#### T25 · 修复「瞬时运动」位移着色的色表范围【A】 ★ 必修

- **现象**：着色选「按帧间位移」、参考选「瞬时运动」时，色条显示范围 `0 ~ 1e-06`。动过的单元全部是饱和的黄色，
  没动的是紫色，颜色只剩两档。「相对 init 结束」「相对输入」两种参考正常（newblue1 末帧范围约 0 ~ 6320）。
- **根因**：`App::updateContinuousValues()` 计算固定色表范围时，只把「最后一帧」传给 `dispMagnitudes()`，
  区间另一端 `H2` 是空指针。`DispRef::Instant` 的定义是 `|pos(hi) − pos(lo)|`，`hi` 为空时位移全是 0，
  第 99 百分位也是 0，最后被 `max(1e-6f, …)` 兜成 `1e-6`。
- **改法**（取最简单的一种）：遍历相邻关键帧对，跳过 `breakBefore` 处的跳变，取所有 `|pos(k+1) − pos(k)|` 的第 99 百分位作为固定范围。
  newblue1 只有 62 帧，全量算一遍也很快，不必抽样。若时间紧，也可以干脆删掉「瞬时运动」这个选项，只留另外两种参考。
- **验收**：newblue1 选「瞬时运动」并在 mGP 中段播放，颜色有明显的连续层次，色条数值不再是 `1e-06`。

#### T26 · 检视面板的 net 列表按 net 去重【A】 ★ 必修

但经 WSLg 显示的程序不会自动放大，于是 17 像素只相当于普通屏幕上的约 11 像素。

**参考商业软件**：在 100% 缩放下，Windows 界面默认字体是 9 pt Segoe UI（约 12 像素），VS Code、JetBrains 系列的界面字号约 13 像素，
macOS 系统字体为 13 pt；在 150% 缩放下对应约 18–20 像素。本项目界面有不少中文，比英文需要稍大一点。

**3. 目标数值**：

| 项 | 现在 | 改为 |
| --- | --- | --- |
| 界面缩放系数 `S` | 无 | 默认 **1.5**（与演示机器的 150% 一致）；命令行 `--ui-scale X` 可覆盖，`viz.sh` 原样透传 |
| 界面字号 | 17 px | 14 px × `S` = **21 px** |
| 控件尺寸（内边距、间距、滚动条、滑块把手、勾选框、标签页、窗口圆角等） | ImGui 默认 | 全部 × `S`：`ImGui::GetStyle().ScaleAllSizes(S)` |
| 收敛曲线（ImPlot） | 默认 | 字号随界面；`ImPlot::GetStyle()` 里的内边距、刻度长度、线宽 × `S` |
| 画布上的文字（坐标读数、刻度、比例尺数字、热力图提示、色条数值） | 17 px | **保持 17 px 不变** |
| 默认窗口 | 1600×980 | 启动时最大化（`GLFW_MAXIMIZED`），`--width/--height` 仍可指定 |

按 §2.5 的演示原则，**不做**自动检测 DPI：WSLg 不向 GLFW 报告缩放比例，`glfwGetWindowContentScale()` 在这里通常返回 1.0，靠不住。写死默认值 1.5 加一个命令行开关即可。

**4. 实现要点**：

- ImGui 1.92 支持全局字号：初始化时设置 `style.FontSizeBase = 14 * S`，并加载字体（加载时的字号不再决定显示字号）。
- **画布文字保持原大小**：`drawCanvasPanel()` 里的 6 处 `fg->AddText(pos, col, text)` 改为显式指定字号的重载
  `fg->AddText(ImGui::GetFont(), kCanvasFontPx, pos, col, text)`，常量 `kCanvasFontPx = 17.f`。
  否则它们会跟着界面一起变大，并且和按像素写死的位置（如 `canvasY_ + 10`、`sy - 6`）错位。
- **代码里写死的像素尺寸要乘 `S`**，否则放大后会截断或溢出：`SetNextItemWidth(160)` / `(120)`、
  `SameLine(GetContentRegionAvail().x - 120.f)`、颜色小方块 `ImVec2(12, 12)`、面板里的色条 `160 × 12` 等。全文搜索 `ImVec2(` 与 `SetNextItemWidth(` 逐个检查。
- **防溢出的三处重点**：
  - 「总览」等「名称 + 数值」两列的地方，改用 `ImGui::BeginTable(..., 2, ImGuiTableFlags_SizingStretchProp)`，不再用 `SameLine(avail - 120)`；
  - 回放按钮那一行（播放、`|< keyframe`、`keyframe >|`、适应窗口）放大后可能超出右栏，宽度不够时自动换行：`SameLine` 之前比较 `GetContentRegionAvail().x` 与下一个按钮的宽度；
  - 滑条、下拉框的标签较长（如「最小显示尺寸（像素）」「net 高亮度数阈值」），改成**标签在上、控件在下占满一行**，避免标签被截在右栏边缘之外。
- **默认布局比例**：右栏由窗口宽度的 22% 改为 **28%**，底部面板由 22% 改为 **26%**；`DockBuilderSplitNode` 两处改数值即可。「重置布局」用同样的比例。
- 旧的 `superplace-gui.ini` 里记着旧的面板尺寸，**改完后删掉它再启动**；演示机器上也要删一次。

#### T34 · GDSII 导出（当前帧，固定路径）【A】

- **入口**：「数据源」的「导出 GDSII」按钮。**不弹窗口、不让选路径**，直接写到
  `<bundle 所在目录的上一级>/gds/<设计>_<阶段>_t<t>.gds`（阶段与 `t` 取当前显示帧），写完在状态栏显示完整路径。
- **导出什么**：当前画面显示的那一帧的位置（暂停在插值中间时就用插值位置）。演示时可以导出 mGP 中间帧与最终帧各一个，在 KLayout 里对比。
- **图层**（与 [05 §5.7.2](05-开发执行规范.md) 一致，datatype 都是 0）：

| Layer | 内容 |
| --- | --- |
| 1 | 标准单元 |
| 2 | 宏单元 |
| 3 | 固定终端（零面积的 `F_NI` 跳过） |
| 10 | Core 边界（`scene.json` 的 `core`） |

  site row（第 11 层）与 filler（第 4 层）不做：录制结果里没有这两类数据（§2.5）。不导出单元名。
- **格式要点**（记录集：`HEADER / BGNLIB / LIBNAME / UNITS / BGNSTR / STRNAME / BOUNDARY / LAYER / DATATYPE / XY / ENDEL / ENDSTR / ENDLIB`）：
  - 全部**大端**；每条记录是 `[2 字节总长][1 字节记录类型][1 字节数据类型][数据]`，字符串补齐到偶数长度。
  - 约定 1 个坐标单位 = 1 µm、数据库单位 1 nm：`UNITS` 写 `(1e-3, 1e-9)`，坐标为 `round(值 × 1000)` 的 `int32`。
  - `UNITS` 的两个数是 GDS 的 **8 字节实数**（excess-64、以 16 为底，**不是 IEEE 754**）。这是唯一容易写错、且一错 KLayout 就打不开的地方，
    **保留一个单测**：断言 `1e-3`、`1e-9` 编码后的 8 个字节与标准值一致。
  - 一个顶层结构，名为设计名；每个节点一个 `BOUNDARY`，`XY` 为 5 个点（首尾相同的闭合矩形）。
- **同步写即可**：newblue1 约 21 MB、1 秒内写完，不需要后台线程与进度条。
- **验收**：newblue1 末帧与一个 mGP 中间帧各导出一次，用 KLayout 打开（使用者自行安装），图层面板能单独开关 1、2、3、10 层，几何与查看器画面一致。

#### T18 · 修复画布鼠标交互（缩放 / 平移 / 点选）【A】 ★ 最先做

> ✅ **已完成（PR #3）**。实机验收：画布中央可平移、以光标为锚缩放（每格 1.28 倍）、点选；F 键适应窗口。F 键与输入框的冲突见 T28。

- **现象**：滚轮和拖动只在窗口左上角约 400×400 像素、且未被其他窗口挡住的一小块区域里有效；
鼠标在画布其余位置时，左上角的读数不显示鼠标坐标（这是「程序认为鼠标不在画布上」的标志）。
- **根因**：`drawCanvasPanel()` 在所有 `ImGui::Begin()` 之外调用，此时 ImGui 的「当前窗口」是隐形的
`Debug##Default`（ini 里记着 `Pos=60,60 Size=400,400`）。而 `ImGui::IsMouseHoveringRect(lo, hi)`
第三个参数 `clip` 默认为 `true`，会先把矩形与**当前窗口的裁剪框**求交（`imgui.cpp` 10882 行），
于是画布的可响应区域被截成了那 400×400。点选也受同样影响。
- **改法**：`app.cpp` 中 `overCanvas` 的判定改为 `IsMouseHoveringRect(lo, hi, /*clip=*/false)`，
并用「鼠标下没有任何 ImGui 窗口」来排除面板遮挡。注意 `io.WantCaptureMouse` 在拖动开始于面板时也会为真，
拖动的「开始点」应该记录在画布上才允许平移，避免从面板拖进画布时误平移。
- **顺带**：滚轮每格缩放 `exp(0.18)≈1.2` 倍，从全图放大到能看清单元要十几格，可以调到 1.25～1.3；
加一个「F 键 = 适应窗口」的快捷键。
- **点选也是这个原因**：`App::drawCanvasPanel()` 里点选同样以 `overCanvas` 为前提，可响应区域之外单击不会触发任何判定。
点选的其余问题见 T24。
- **验收**：画布任意可见位置都能缩放、平移、点选；鼠标在面板上时滚轮只滚动面板、不缩放画布；
左上角读数在画布任意位置都显示鼠标坐标。为相机交互补一个无头测试较难，至少在 PR 里附操作录屏或截图。

#### T24 · 检视与点选可用性【A】 紧接 T18

> ✅ **已完成（PR #3）**。实机验收：「检视」独占右下节点；newblue1 全图视角下单击即选中标准单元并显示网表信息；选中标记至少 8 像素，跟随回放插值。遗留：取消选中后读数残留（T28）、容差点选缺单测（T29）。

- **现象**：在画布上单击，「检视」面板始终显示「单击画布节点进行点选检视」，看起来功能完全无效。
- **根因**（2026-11-04 实测 + 代码核对，四个原因叠加，修掉任何一个单独都不够）：
  1. **悬停判定**：与 T18 同一个原因，窗口左上角约 400×400 像素之外单击不触发点选。
  2. **结果看不到**：默认布局把「控制」「检视」停靠进**同一个节点**（`app.cpp` 两次 `DockBuilderDockWindow(..., right)`），

     成为两个标签页，默认显示「控制」。即使点中了，结果也藏在没打开的标签页里，而且不会自动切换过去。
  3. **几乎点不中**：`SpatialIndex::pick()` 按**真实几何**判定命中。newblue1 全图视角约 0.043 px/unit，

     标准单元宽 6～9 个单位，在屏幕上只有 0.3 像素左右；画面上看到的「点」是亚像素保护放大到 1.5 像素后的效果，

#### T20 · 全图默认画真实矩形，热力图改为图层开关【A】（2026-11-04 已与算法侧确认方案）

> ✅ **已完成（PR #3）**。实机验收：全图默认显示真实矩形；取消「标准单元」后单元消失；局部密度着色与类别明显不同；矩形模式回放基准见 §5.1。遗留：图例单位文案（T28）、热力图开关应移到「图层」栏（T29）。

- **现象**：在全图视角下切换图层、切换「按局部密度 / 按类别」、拖动最小像素，画面都毫无变化。
- **根因**：`lodActive_ = lodAuto_ && rowPx < 15`——行高在屏幕上不足 15 像素就只画 128×128 的密度热力图，
`canvas_.draw()` 根本不调用。newblue1 行高 12、全图视角约 0.043 px/unit，一行不到 1 像素，
要放大约 29 倍（视野只剩芯片宽度的 7%）才会出现真实矩形。而图层开关、着色模式、最小像素

这三项功能本身是实现了的，只是在默认视角下永远看不到。
另外热力图在全图下呈块状，用户很容易把它误认为「单元」。
- **决定**：
  1. **默认画真实矩形**。实测全图画 33 万矩形只需约 1.8 ms（§5.1），不需要 LOD 来保性能。
  2. 密度热力图改为「图层」里的一个开关（默认关），打开后叠加在矩形上（可调透明度）。
  3. 只有当**节点数超过约 100 万、且行高在屏幕上不足 1 像素**时，才自动降级为热力图；

     降级时在画布上方显示明确提示：「热力图模式：图层 / 着色在此模式下不生效，放大后恢复」。
  4. 删掉「近景叠加密度热图」「远景自动 LOD 热力图」两个旧选项，避免概念重叠。
- **顺带修**：
  - 「按局部密度」用的色表（蓝→绿→红）和类别配色（标准单元恰好是红色）撞色。在 init 帧所有单元挤在中间、密度都高，
  于是两种模式都是一片红，看起来「没有区别」。连续色表换成与类别色区分明显的 viridis 一类色表，
  并在画布角落画色条图例。
  - 「最小像素」改名为「最小显示尺寸（像素）」，加悬停说明：「全图视角下单元不足 1 像素，
  按此尺寸放大显示，避免碎成噪点」。
  - `canvas.cpp` 里 `glActiveTexture(0)` 应为 `glActiveTexture(GL_TEXTURE0)`（0x84C0），
  现在每帧产生一次 `GL_INVALID_ENUM`。
- **验收**：newblue1 全图视角下，取消「标准单元」图层后红色单元消失；切到按局部密度后颜色明显不同于按类别；

（这也补上了 §8.2 里「矩形模式回放没有基准」的缺口），播放时 p95 不超过 33 ms。

#### T15 · 修复 `FrameView` 悬垂指针【A】 阻塞 T14，必须最先做

> ✅ **已完成（PR #2，2026-11-04）。** 验证：62 帧 newblue1 上持有第 30 帧再读 61 帧，数据零改动、缓存 ≤ 24 帧；
> 第 3/20/30/40/51/61 帧截图两两不同；ASan+UBSan 0 报告。红测在 `gui/test/test_frameview_lifetime.cpp`。

- **现象**：用 CLI 录制的 62 帧 newblue1 bundle 打开 PR #1 的查看器，远景热力图在
**每一帧都画错**：`--frame 3 / 20 / 30 / 61` 实际画的是第 53 / 45 / 49 / 49 帧；
从第 30 帧起截图逐像素相同。矩形模式是对的（位置在 `gotoFrame` 时就上传了 GPU）。
- **根因**：见 [§8.3 坑（5）](#83-已经踩过的坑改渲染布局或数据层时留意)。一句话：`FrameView` 用裸指针指向
LRU 缓存（24 帧），T5 构建帧↔行映射时对全部帧调用 `frame()`，把当前帧挤出缓存，
之后热力图 / 点选 / 着色懒计算时读到的是被复用的内存。
- **复现**（算法侧给你 bundle 后）：
  ```bash
  ./build/superplace-viz newblue1/viz --frame 30 --shot-after 4 --screenshot a.ppm
  ./build/superplace-viz newblue1/viz --frame 61 --shot-after 4 --screenshot b.ppm
  cmp a.ppm b.ppm && echo "仍有问题：两帧画成了同一个画面"
  ```
- **修法（两处都要做）**：
  1. **数据所有权进契约**：`FrameView` 改为持有 `std::shared_ptr<const std::vector<float>>`，

     `x` / `y` 由它派生；缓存也存 `shared_ptr`。缓存淘汰只是放掉缓存自己的那份引用，
      任何还拿着 `FrameView` 的地方数据都活着。零拷贝，整类问题一次消失。
  2. **元数据不该触发 I/O**：`IPlacementSource` 加一个 `frameInfo(int i)`，返回

     `stage / iter / t / breakBefore / label`，**不读位置文件**。T5 的映射、进度条刻度只用它。
      现在 T5 首次画曲线会把 62 帧共 162 MB 全读一遍，这本身也是个启动卡顿。
- **不要用的修法**：调大缓存（只是推迟触发）；只在 `gotoFrame` 里给 `cur_` 拷一份
（T8 两帧对比拿的 `fa` / `fb` 一样会中招）。
- **验收**：新增无头测试——取第 N 帧后再取 ≥ 25 个其他帧，原 `FrameView` 的数据逐位不变
（**这个测试在现有实现上必须失败**，先写测试再修）；上面的复现命令四帧截图两两不同；
任一帧的热力图与按该帧文件独立计算的密度一致。
- **估时**：半天。

#### T14 · 连续回放：插值 + 断点 + 按迭代速率播放【A】 ★ 本阶段主线

> ✅ **已完成（PR #2，2026-11-04）。** 实现在 `gui/src/viz/playback.{h,cpp}`。验证：4001 个采样点上跨断点插值 0 次，
> init / mLG 断点帧可单独停住，两帧中点 alpha=0.500；newblue1 总时长 11.35 s = 591 轮 ÷ 60 轮/秒 + 3 个里程碑各 0.5 s。

- **前置**：T15。
- **时间轴用** `t`**，不用帧序号**：进度条横轴是全局迭代数 `t`（§3.2）。播放速度的单位是
"轮/秒"（例如默认 60 轮/秒，newblue1 的 591 轮约 10 秒放完）。
不带 `t` 的 bundle（合成样本、`make_viz.py` 转换的）退化为按帧序号均匀分布。
- **插值**：当前 t 落在相邻帧 k、k+1 之间，且第 k+1 帧**不是** `breakBefore` 时，
位置 = 两帧线性插值。CPU 上做即可（33 万节点每次不到 1 ms）；百万节点以上再改为
在顶点着色器里混合两组实例缓冲（只在跨过关键帧时上传，拖动时零上传）。
- **断点**：`breakBefore` 处必须**硬切**（目前是 init 与 mLG 两处）。插值会画出宏
"滑到合法位置"的假动作，看着顺眼但不是真实过程。t 相等的相邻帧视为瞬时切换；
里程碑帧（`iter = -1`）播放时停留一小段固定时长（如 0.5 s），否则 input → init 一闪而过。
- **进度条**：按 `stage` 分色；显示当前帧 `label`；与收敛曲线的游标双向联动（复用 T5）。
- **交互**：播放 / 暂停、调速、跳到上 / 下一个关键帧、跳到上 / 下一个阶段、循环开关、拖动。
- **懒计算在插值帧上的语义**（热力图、点选索引、属性着色）：拖动或播放时按**最近的关键帧**
计算，停下来再按插值后的位置重算。要在界面上让人知道当前显示的是哪一帧的统计。
- **热力图在回放时会"闪"**：PR 的热力图按**每帧自己的 maxNorm** 归一化，而 newblue1 第 30 帧
maxNorm 是 15.9、最终帧只有 1.2——同样的密度在不同帧里颜色完全不同。
回放模式要用**固定标尺**（按目标密度 1.0，或全片最大值），否则颜色变化会盖过真实的扩散过程。
- **验收**：newblue1 的 62 帧 bundle 从头放到尾不卡顿（≥ 30 fps）；mLG 处宏硬切、不滑动；
与 `m3-artifacts/mms-adaptec1-convergence.gif` 目视对比，连贯程度不低于它；

### 9.3 第二批 · 核心能力（全部【A】，约 1–2 周）

**这一批是查看器真正的价值所在**，也是工作量主体。T4 是后面几项的前提，先做。

#### T4 · 空间索引 + 点选 + 检视面板【A】 ★ 最大的一块

- **为什么最重要**：它是 T7、T8、T10 的共同前提。没有点选，查看器只能"看个大概"，
回答不了"这块密度为什么这么高""这个宏周围的单元被谁拉过去了"这类真问题
（[01 §7.1](01-架构设计与技术选型.md) 说的交互式空间探索）。
- **技术要点**：**33 万节点不能线性扫**。建一个均匀网格索引即可：
按 `chip` 划成 ~256×256 的桶，每桶存落入其中的节点下标（CSR 两趟构建，
和算法侧 `PlaceDB::finalizeCSR` 同一套路）。点选时只查鼠标所在桶及其邻域。
- **坑一**：**位置每帧都变**，索引必须跟着重建。好在单帧重建是 O(N)，
330k 节点约几毫秒；但**不要每帧都建**，只在切帧后第一次点选时懒重建。
- **坑二**：命中判定要用**真实矩形**而非渲染时被亚像素保护放大后的矩形，
否则全芯片视角下点哪儿都能"命中"一片。
- **坑三**：重叠时该选谁。建议按"面积最小者优先"，否则点宏上面的标准单元永远选不中。
- **检视面板显示**：名字（依赖 T9）、下标、类别、宽高、中心坐标、所属 bin。
- **验收**：330k 节点上点选响应无可感延迟；选中项在画布上高亮；
点空白处取消选中。

#### T5 · 收敛曲线改造【A】

- **现状**：横轴用的是**行序号**而非真实迭代数。因为 `metrics.csv` 的 `iter` 列··  
在每个阶段都从 0 重数，直接当横轴会让曲线在阶段交界处折回去，看着像发散。
- **做什么**：按阶段拆成多条序列（mGP / FILLERONLY / cGP 各一条，不同颜色），
横轴仍用累计序号但 tooltip 显示"阶段 + 阶段内迭代数"。
- **联动**：拖时间轴时曲线上出现游标；反过来点曲线能跳到对应帧。
注意 bundle 的帧数远少于 metrics 的行数（帧是抽样的），要做一次映射。
CLI 录制的 bundle 每帧带 `stage` 与 `iter`，可以**精确**对应到 `metrics.csv` 的一行。
- **⚠️ 建映射只能读元数据**：不要为了拿标签对每一帧调用 `frame()`——它会把位置数据
也读进来并挤掉缓存，这正是 T15 那个问题的触发点。用 T15 新增的 `frameInfo()`。
- **验收**：newblue1 上三个阶段分色清晰；拖时间轴游标同步移动。

#### T6 · 密度热力图 + 远景 LOD【A】

> ⚠️ 2026-11-04 试用后决定：全图默认画真实矩形，热力图改为图层开关，见 [T20](#t20--全图默认画真实矩形热力图改为图层开关a2026-11-04-已与算法侧确认方案)。下面是原始需求，保留作记录。

- **做什么**：由当前帧位置**在查看器里现算** bin 密度（不必加进 bundle），
画成热力图叠加；缩放比例小于某阈值时自动从"画真实矩形"切到"画热力图"。
- **为什么要 LOD**：全芯片视角下标准单元只有亚像素大小，现在靠亚像素保护硬撑成
1.5 px，看到的其实是噪点而不是信息。热力图才是那个尺度上有意义的呈现方式。
**KLayout 就是这么做的**（[01 §7.4](01-架构设计与技术选型.md)）。
- **算法**：累加每个节点与 bin 的重叠面积即可，不需要算法侧那套 local smoothing
与密度缩放规则（那是给优化器用的，这里只是可视化）。**但要写清楚这一点**，
否则日后会有人拿它和引擎的 τ 对不上而困惑。
- **验收**：热力图与同一帧的 PNG 在视觉上吻合；切换 LOD 时无跳变感。

#### T7 · 按属性着色【A】

- 可切换：按类别（现状）/ 按局部密度（复用 T6）/ 按相对上一帧的位移量 / 按 net 数。
- **实现**：给实例缓冲加一个 `float aValue`，片元里查颜色表。渲染路径改动很小。
- **验收**：切换即时生效；配色有图例与数值范围。

#### T8 · 两帧对比与位移矢量场【A】

> ⚠️ 2026-11-04 试用后决定取消独立的对比面板，由 [T21](#t21--取消帧对比面板位移改为着色模式--箭头图层a2026-11-04-已与算法侧确认方案) 取代。下面是原始需求，保留作记录。

- **做什么**：同时取两帧，用颜色（位移大小）或线段（位移方向）表示单元的移动。
- **用途**：一眼看出 mLG 把哪些宏挪了多远、cGP 把哪些单元重新拉回去了。
- **提示**：`BundleSource` 的 LRU 默认缓存 24 帧，取两帧不会触发反复 I/O。
- **验收**：MMS 数据上能清楚看出 mLG 前后宏的位移。
