# 07 · M3 问题台账与回归防护

> 本文写给**接手 M3 后续优化的同伴**。M3（ePlace 四阶段：mGP → mLG → FILLERONLY → cGP）
> 的代码和参数经过了很多轮反复调整，每一处都有它的来历；改动之前不了解来历，最容易把
> 修好的问题改回去。本文把 M3 期间发现过的**全部问题**列成台账，按当前状态分成三类：
>
> - **已确认未复现**：全量回归的数据足以证明它没有回来；
> - **无法从数据确认**：在一次运行的结果里看不出来，只能靠单元测试或专门实验守护；
> - **仍未解决**：数据里还看得到，或者只是绕过、没有根治。
>
> 后半部分是**开发时避免回归的规则**、**每次改动后的验证流程**和**接下来的任务**。

> 它在 05 里的详细位置）、[04 Benchmark 调研与获取指南](04-Benchmark%20调研与获取指南.md)。
>
> **状态截至 2026-11-10。** M3 最后一次算法改动是提交 `7692b32`（2026-11-10，mLG 修复改进、
> 可选的相对 λ 调度、可复现的回归诊断工具）。此前的里程碑：`2413a0e`（10-27，回溯校验、
> 停滞保护、连锁推挤）、11-05 的黄金测试与 CUDA 泊松后端。11-09～11-10 的实验报告原为单独的

### 1.3 工具

**当前口径的工具**（11-10 起，`7692b32`）：

| 工具 | 用途 |
| --- | --- |
| `scripts/m3_audit.py --bin <CLI> --out <目录> [--bench-root <目录>] [--designs …] [--seeds …]` | 按当前口径逐设计生成配置并运行，固定 CPU、16 线程；每次运行写 `manifest.json`。续跑时检查二进制、配置、输入路径和线程数，**拒绝混用**。默认 `--bench-root` 是同伴机器的路径，本机要显式传 `--bench-root benchmarks` |

| `superplace-cgp-ablation` | 在同一份 FILLERONLY 后的内存初态上运行多组 cGP 变体（关闭回溯、冻结 γ/λ、filler 预热 100 轮等） |

**黄金测试的边界**：它守的是"给定配置的 CPU 路径逐位不变"，不判断结果好坏。thin1 的 τ 初值为 0，
GP 不迭代，它实际只守 QP 与"已达标不动"；mGP、mLG、cGP 由 adaptec1 与 MMS adaptec1 覆盖。
回溯较多（MMS newblue1）和触发停滞（MMS bigblue2）的设计不在黄金集里，相关改动要手工补测（§7.3）。

**GPU 结果另有基线，不参与 CPU 黄金比对。** `poisson_backend="cuda"` 时 cuFFT 与 FFTW 的舍入不同，
场的逐点差约 1e-6（05 §7.4），经过几百轮非凸迭代后 `.pl` 必然与 CPU 不同，这是预期行为。
GPU 路径的守护是：`test_poisson`（CUDA 那一遍）与 `test_poisson_parity` 的对拍判据；同一 GPU 上
两次运行 `.gp.pl` 逐字节相同；以及把 `results/e2e_gpu*` 当作 GPU 的对照基线（只比是否在噪声内，见 §7.5）。

### 4.1 MMS newblue4 的 cGP 不达标

- **现象**：当前口径（密度 0.5，目标 0.10）下，基线 cGP 停在 τ=0.1343。11-10 的 mLG 改进后五个种子为：

  | 种子 | 交付 τ | cGP 轮数 | cGP 期间宏位移数 |
  | ---: | ---: | ---: | ---: |
  | 1002 | 0.13521 | 319 | 0 |
  | 1 | 0.13555 | 319 | 0 |
  | 2 | 0.13498 | 321 | 0 |
  | 3 | 0.13474 | 321 | 0 |
  | 4 | 0.13524 | 318 | 0 |

  历史口径（密度 1.0，目标 0.07）下同样不达标：停在 0.0876，更早还有 0.0820，**是原有问题**。
  其余 15 个 MMS 设计的 cGP 都正常达标。
- **已排除的可能**：
  - 同一份 FILLERONLY 后内存初态上的 5 组消融都在 τ≈0.13 停下，均未达标（宏坐标都不变）：

    | 实验 | 交付 τ | HPWL | cGP 轮数 |
    | --- | ---: | ---: | ---: |
    | 基线 | 0.13432 | 2.2663e8 | 317 |
    | 关闭回溯 | 0.13478 | 2.2660e8 | 321 |
    | 固定初始 γ | 0.13183 | 2.2984e8 | 314 |
    | 固定初始 λ | 0.33552 | 2.2542e8 | 201 |
    | FILLERONLY 加到 100 轮 | 0.13214 | 2.2651e8 | 294 |

    所以问题与回溯、γ/λ 调度、filler 预热都无关。
  - 电荷守恒：1024² 网格上，单元电荷约 9.856e7、filler 2.875e7、固定终端 3.837e7；独立逐节点采样的电荷 1.2732e8
    与网格动态电荷之和一致到输出精度，没有面积丢失。冻结后容量 1.6618e8，动态电荷、终端电荷与暗节点合计约 1.6616e8，
    没有全局超容。
  - 冻结的宏正确地从动态项转入终端项，二者都乘了目标密度；`test_density`、`test_eplace` 的相关用例均通过。
- **根因**：**未定位**。以上都是全局性的必要条件检查，不能解释**局部**停滞。没有放宽阈值，也没有改用更粗的网格。
- **建议**：见 [§8 任务 1](#8-接下来的任务)。

### 4.2 ISPD newblue4 的 mGP 不达标

- **现象**：当前口径（密度 0.5）下，基线与候选的默认种子 mGP 都停在 τ=0.1554。这个设计没有可移动宏，
  mGP 的结果就是最终交付，所以它是**最终未达标**。
- 历史口径（密度 1.0）下 τ 停在 0.1012~0.1031：这个设计 τ 能降到的下限贴着 0.10，不开回溯时 3 个种子刚好擦线达标
  （0.0998 / 0.1000 / 0.0999），开回溯时停在 0.1007~0.1012（`results/nb4/`）。
- **根因**：当前口径下**未分析**。密度从 1.0 降到 0.5 后离目标更远了，需要先看 τ 的下限是不是被固定对象的分布决定的。
- 不要为它单独调 `gp_stagnation_min_gain`，那个门槛的依据是全体设计（[§6.3](#63-参数改动之前先看它的依据)）。

### 4.3 ISPD bigblue3 的 mGP：两台机器表现不同

- **现象**：同样的目标密度 1.0，本机 10-27 的 `audit5` 中 mGP 第 382 轮收敛（τ=0.0991）；
  同伴机器 11-10 的基线停在 τ=0.1608。后续 mLG、cGP 达标，最终交付没有问题。
- **根因**：**未分析**。两边代码版本、cGP 目标都不同，但 mGP 阶段只受目标密度和 mGP 参数影响。
  最可能的解释是两台机器的浮点细节不同（§4.7），被这个设计的非凸轨迹放大成了收敛与否的差别。
  它说明 bigblue3 的 mGP 收敛对数值细节很敏感，是一个稳定性问题。

### 4.4 MMS bigblue2 的 mGP 平台期

- **现象**：当前口径下 mGP 停在 τ=0.1659，历史口径下停在 0.162，都被停滞保护截停后交给 mLG，最终 cGP 达标。
- **根因（已查清，10-27）**：剩下的溢出来自宏与宏之间的重叠，密度力推不开；mLG 消掉宏重叠后 τ 立即降到 0.138 左右。
  这部分本来就该交给 mLG，**属于设计预期**。列在这里是为了说明这类"mGP 未达标"不必修，并与 §4.3、§4.5 区分。

### 4.5 MMS newblue6 的 mGP 稳定性

- **现象**：当前口径（密度 0.8）下，种子 3 的 mGP 停在 τ=0.2635，第 711 轮回退到第 510 轮，后续 cGP 达标（0.0991）。
  默认种子虽然达标，却要 1778 轮，是全集最多的。候选与基线共享同一份 mGP，所以不是 11-10 的 mLG 改动引入的。
- **根因**：**未分析**。完整运行在 `results/m3/baseline/mms/newblue6/seed-3/`。
- 不能据少数重点设计降低 `gp_max_iter`。

### 4.6 λ 调度的参考尺度不随设计规模缩放

- **现象**：MMS bigblue4 前 150 轮 λ 缩小了 45~76 倍，τ 几乎不动；当前口径下五个种子要 1227–1254 轮才收敛（ISPD 版约 290 轮）。
- **根因（已查清）**：`delta_hpwl_ref = 3.5e5` 是 ePlace 在 ISPD 规模下给的固定常数。bigblue4 早期每轮 HPWL 涨约 2e6，
  μ 被压在下限 0.95。
- **11-10 的尝试**：新增可选的 `lambda_schedule="relative"`，参考量改为阶段初始 HPWL × `delta_hpwl_relative`
  （阶段内固定，FILLERONLY 仍用固定参考量）。以 MMS adaptec1 的 mGP 初始 HPWL 标定出基准系数约 0.0209，试了 0.5/1/2 倍：

  | 尺度倍数 | MMS newblue4 最终 HPWL / τ | MMS bigblue4 mGP 轮数 / 求值次数 | MMS bigblue4 最终 HPWL |
  | --- | ---: | ---: | ---: |
  | fixed（对照） | — | 1252 / 1264 | 6.391e8 |
  | 0.5 | 2.2910e8 / 0.1379 | 958 / 969 | 1.965e9（+207.5%） |
  | 1 | 2.3260e8 / 0.1341 | 454 / 463 | 1.356e9（+112.2%） |
  | 2 | 2.3375e8 / 0.1339 | 277 / 285 | 8.425e8（+31.8%） |

  2 倍档的五种子配对验证：newblue4 +3.29%、bigblue4 **+84.62%**，都超过 3%，**否决**。
- **现状**：默认 `fixed`，`gp_max_iter` 保持 2000。为什么迭代少了线长却大幅变差，**未分析**。
  一个推测是参考量变大后 λ 涨得太快，密度力在线长还没优化好时就压过了线长力，单元被过早铺开。

### 4.7 黄金值跨环境不一致

- **现象**：同伴环境下（x86_64、GCC 13.3.0、Ubuntu 24.04、FFTW3f 3.3.10、Release、`ENABLE_NATIVE=ON`），
  **未修改的算法**输出也对不上本机 11-05 生成的历史黄金值，例如 thin1 的 `init.pl` 哈希为
  `06dce937…a7c8`。同时它自己的 1/8/32 线程输出是一致的。
- **处理**：历史黄金值保留在 `test/golden/*.sha256`，改为显式开启 `-DENABLE_LEGACY_GOLDEN=ON` 才注册（`-L legacy`）；
  当前口径的黄金值在 `test/golden/m3/`（`configs/m3/golden.json`，cGP 0.10），由同伴环境生成，默认注册（`-L m3`）。
- **根因**：**未查清**。怀疑对象：`ENABLE_NATIVE=ON`（`-march=native` 让编译器按各自 CPU 生成不同的向量指令与 FMA）、
  编译器版本、Eigen/FFTW 版本。
- **影响**：黄金测试目前只在生成它的环境里有效。`test/golden/m3/` 在本机**很可能对不上**；也就是说，
  换一台机器时，黄金测试失败不能直接说明代码有回归。§4.3 很可能也是同一来源。

### 4.8 SA 消除重叠的能力有限

- 19 个带宏设计里，有 9 个 SA 完全没有减少重叠，重叠全靠贪心修复消掉（各日志的"mLG 分账"行）。
- 原因在代价函数：位移项让 SA 不愿乱跑，而消除重叠必然要付位移代价。05 §5.6.2 有详细分析，并给出了长期方向
  （"先合法、再精修"）。**这是已知的设计张力，不是回归。**

### 4.9 没有可靠的性能回归检测

- 跨会话计时不可靠（混合架构 CPU、WSL、其他负载）。要判断"变快 / 变慢"，必须**在同一会话里背靠背**重跑基线与新版本。
- 现在有了与机器无关的工作量计数（CSV 的 `evaluations`、各阶段轮数），但还没有纳入任何闸门（§9 P3-2）。

### 4.10 工具、数据与仓库的坑

- **验收口径改过**：`configs/default.json` 的 `cgp_target_overflow` 已从 0.07 改为 0.10，`plot` 改为 `false`。
  11-10 以后的所有数字都不能和 `audit5*` 直接比较；运行旧黄金或旧对比时要显式用 `configs/m3/legacy-golden.json`。
- **两套工具并存**：历史的 `run_audit.sh` / `compare_audit.py` 与当前的 `m3_audit.py` / `m3_compare.py`
  口径不同、输出目录结构不同，不要混用。
- **当前口径的原始数据不在仓库里**：`results/m3/` 只在同伴机器上；`m3_audit.py` 的默认 `--bench-root`
  是同伴机器的路径，本机要显式传。
- `scripts/run_audit.sh` 按设计名命名日志，**ISPD 与 MMS 有同名设计**（如 newblue4），放进同一个输出目录会互相覆盖。
  `m3_audit.py` 按 `<suite>/<设计>/seed-N/` 分目录，没有这个问题。
- `build_clean/` 下的二进制和目标文件被 git 跟踪，每次编译都会出现在 `git status` 里，提交时要注意别混进去。
- `scripts/make_mms.py` 已废弃（adaptec4 的数据是错的），不要再用。

| **mLG 远距离挪动**（MMS newblue3 修复后最大位移 15302，bigblue2 9560） | 根因已查清并修复（L12–L14）：分离平移的方向平局取了第一个方向。同一 `.mgp.pl` 回放中 newblue3 最大位移 15877 → 5448、bigblue2 1758 → 1487。必须远移时，放开距离的搜索仍会作为兜底 |
| **宏平均位移上升与几处小幅退步重合**（ISPD newblue2/bigblue3、MMS bigblue1/newblue5 位移上升，HPWL +0.3%~+1%） | 用 mGP 快照做了当初建议的同输入回放：19 个含宏设计中修复算法在同一输入上没有让位移变大（17 个最大位移下降、2 个持平）。端到端五种子数据也显示 95 对运行位移都不增加。注意：位移改善不能直接当作最终 HPWL 改善，HPWL 以 §1.4 的五种子结果为准 |
| **ISPD newblue1 的 +15.3%**（10-27，开回溯后） | 种子运气，不是退步。不回溯时 5 个种子在 7.2e7~13.7e7 之间大幅波动，默认种子恰好最好；回溯后在 7.5e7~8.2e7 之间、均值低 17%。11-10 的默认种子 +1.65%、五种子 −0.17% 再次印证。**不要为它"修回去"** |

## 5. 走过的误判：哪些结论曾被推翻

这些都写进过对话或文档，之后被实测推翻。列在这里，是为了让接手的人在得出类似结论时多一分警惕。

| 曾经的结论 | 实际情况 | 教训 |
| --- | --- | --- |
| "QP 提速 1.6 倍" | 是在已撤销的 cap=50 配置下测的，实际交付只快约 9% | 报告提速要说明配置，且只在同一会话里比 |
| "QP 的瓶颈在 `setFromTriplets`" | 只在小设计上成立；大设计的瓶颈是零对角补丁（Q2） | 小设计上剖析出的瓶颈不能外推 |
| "MMS 两个设计最终 HPWL 退了 2.4–3.8%，是新改动引入的回归" | 是 mLG 缺位移项（L1）这个旧缺陷被新轨迹暴露了 | 先区分"引入"与"暴露" |
| "τ 平台期是数据造成的假象" | 对重建版 adaptec4 成立，但官方 MMS 上 5/16 个设计的平台是真实的 | 一个反例不足以推广 |
| "binDim 公式太激进" | 公式与 DREAMPlace 一致；512 网格只是把热点藏住了，换成 1024 网格测 τ=0.2616 | **不同网格分辨率下的 τ 不可比** |
| "早期步长尖峰在 τ 高时无害" | 不影响收敛，但会抬高最终线长（G6） | 看最终线长，不只看是否收敛 |
| "单测要跑 170 秒，太慢" | 测试本身 4 秒，慢是机器争用造成的 | 计时异常先排除环境 |
| "照搬 DREAMPlace `step_nobb` 就能修好不收敛" | adaptec5 最优 τ 只到 0.2676，比不修还差 | 换方案前先弄清它在自己数据上为什么有效 |
| "ISPD newblue1 +15% 是回溯造成的退步" | 是默认种子运气好（§4.11） | 混沌敏感的设计要看多种子分布 |
| "宏位移上升是修复顺序造成的" | 同输入回放显示修复算法本身没有让位移变大；真正的远跳来自分离平移的方向平局（L12） | 用同一输入回放，分清"算法"与"输入" |
| "历史黄金测试失败，说明本轮算法改坏了" | 同伴环境下未修改的算法也对不上历史黄金值（§4.7） | 黄金值失败先确认是否同一环境 |
| "相对 λ 尺度让迭代大幅减少，是改进" | 迭代减少的同时 bigblue4 线长差了 84.6%（§4.6） | 不能用迭代次数代替质量验收 |
| "mLG 位移改善就能修好 newblue4 的 cGP" | mLG 改进后五个种子的 cGP 仍全部停在 0.135 左右（§4.1） | 上游指标改善不等于下游问题解决 |

## 6. 开发规则：怎样避免把修好的问题改回去

### 6.1 碰这些代码之前，先读对应的注释和 05 章节

下列位置都有"为什么必须这样写"的注释，改之前先读，**不要只凭直觉"简化"**：

| 位置 | 看起来可以简化的地方 | 为什么不能动 |
| --- | --- | --- |
| `src/numeric/cpu/nesterov.cpp` `redoIfOvershot` | 改成在步末试走求值（DREAMPlace 写法） | G9：下降方向会用到过时的 λ、γ |
| 同上，`vPrev_.swap` 和 `momentumPrev_` | 看起来是多余的状态 | 重走上一步要用 v_{k−1} 和上一步的动量系数 |
| `src/gp/eplace.cpp` 达标时的 `s.pos = s.lastEval` | 直接交付 `s.pos` | G4：交付点必须是测得 τ 的那个点 u |
| 同上，停滞快照从 `lastEval` 拷坐标、`Snapshot` 阶梯 | 存 `s.pos`；只存一个最优点 | G3、G8（`testStagnationRollbackPoint` 会变红） |
| 同上，`objAndGrad` 里 `scatter(p)` 后拷贝 `lastEval` | 改回"db 此刻停在 u 上"的隐式约定 | 将来 GPU 常驻时 db 不再与求值点同步；`onIter` 回调前届时要显式同步 |
| `src/gp/lambda_schedule.h` | 把 `relative` 设为默认 | §4.6：五种子验证线长恶化 84.6%，已否决 |
| `src/lg/macro_sa.cpp` 修复顺序（分离 → 推挤 → 限距网格 → 放开） | 换回网格搜索打头 | L10：大宏会被粗网格扔到远处 |
| 同上，分离平移的方向平局按距 mGP 原位选择、整轮新旧比较只在三项都不增加时接受 | 取第一个可行方向；只比较重叠 | L12：会出现不必要的大幅移动 |
| 同上，`src/lg/repair_candidates.h` 的接触点与相邻 site/row 候选 | 只用固定步长的网格候选 | L13：粗采样会跳过狭窄的合法区 |
| 同上，最终回拉前重建增量线长缓存 | 直接用 SA 留下的缓存 | L14：会把 SA 的旧缓存当作修复后的当前值 |
| 同上，`gridRepair` 里没有 `break` | "一轮没进展就退出"看起来更省时 | L9：窗口来不及放大 |
| 同上，`OverlapModel` 只有 `setPos` 一个写入口、候选要排序 | 调用方另存坐标、去掉排序 | L6、铁律 7 |
| 同上，`dispOf` 量的是离 **mGP 原位**的距离 | 改成离当前位置 | L2 |
| `src/init/quadratic_placer.cpp` 串行装配、`(i,i,0)` 预留对角 | 并行装配；删掉"值为 0 的三元组" | Q2、Q3 |
| `src/gp/bin_grid.cpp` 固定 8 个分块 | 按 `omp_get_max_threads()` 分块 | U1、铁律 7（黄金测试的 1/32 线程用例会变红，已实测） |
| `src/numeric/poisson_factory.cpp` 是唯一的 `#ifdef ENABLE_CUDA` | 在接口头或 `bin_grid` 里按构建分支 | 铁律 5 |

### 6.2 读数纪律

1. **含可移动宏的设计对数值细节混沌敏感。** 只差 0.05% QP HPWL 的变体，最终结果能差 ±3%，外加 25% 的离群。
   **单次运行 1~3% 的差异不足以判断改好还是改坏**；验收按 §1.1 的五种子配对口径。
2. **不要在纯标准单元设计上调参数。** ISPD 里只有 newblue1、newblue2、bigblue3 有可移动宏，
   其余 13 个对 QP 初值、mLG 都不敏感，在它们上面调出来的参数在 MMS 上会变差（05 §5.4.5.1 有实例）。
3. **τ 只能在同一网格、同一分母、同一口径下比较。** mLG 把宏钉死后，宏面积从 τ 的分母里消失，
   τ 会"跳"一下（MMS adaptec1 分母缩小 2.32 倍）；mGP 与 cGP 的网格分辨率也可能不同；
   历史口径与当前口径的目标密度不同。
4. **判断"引入"还是"暴露"。** 一个改动让某设计变差时，先在同一输入上分别回放新旧代码
   （mLG 用 `superplace-mlg-replay` 或 `m3_replay.py`，mLG 之后的阶段用 `superplace-m3-pair`），再下结论。
5. **"收敛"不等于"好"，"迭代少"也不等于"好"。** 同时看最终 HPWL、mLG 位移、mLG 后的 τ（G6、§4.6）。
6. **跨机器的数字不逐位可比。** 黄金值、基线哈希只在同一环境下有意义（§4.7）。

### 6.3 参数改动之前先看它的依据

| 参数 | 当前值 | 依据 | 改它会影响什么 |
| --- | --- | --- | --- |
| `target_density` | 默认 1.0；当前口径逐设计设定 | §1.1 | 所有设计的轨迹与 τ |
| `cgp_target_overflow` | **0.10**（11-10 由 0.07 改） | 当前口径 | 所有含宏设计的 cGP 停止点；与历史数据不可比 |
| `gp_backtrack` | `true` | G5、G6、§4.11 | 所有设计的 mGP 轨迹 |
| `gp_stagnation_window` | 200 | 收敛设计里有 100 轮 τ 完全不降的正常停顿（λ 爬坡早期） | 改短会误截收敛设计 |
| `gp_stagnation_min_gain` | 0.02 | 全部收敛设计任意 200 轮内最优 τ 至少改善 7.1%，2% 留 3.5 倍余量 | 改大会误截慢收敛设计；改小会让 G7 复现 |
| `gp_max_iter` | 2000 | MMS bigblue4 需 1227–1254 轮；当前口径全集最大 1778 轮（MMS newblue6） | 改回 1000 会让这些设计跑满 |
| `lambda_schedule` / `delta_hpwl_relative` | `fixed` / 0.01 | §4.6：relative 已否决 | 改成 relative 会大幅恶化线长 |
| `density_chunks` | 8 | 扫过 4~32 实测；与线程数无关 | 必须保持固定值，不能随线程数变 |
| `qp_tol` / `qp_outer_tol` / `qp_solver_max_iter` | 1e-6 / 1e-4 / 100 | Q1；真正的预算旋钮是 `qp_solver_max_iter` | 放松 `qp_tol` 不会提速，只会让迭代次数不可控 |
| `macro_sa_disp_weight`（δ） | 1.0 | L1 | 改成 0 会让 mLG 重新布图 |
| `poisson_backend` | `"cpu"` | CPU 路径是黄金基线；`"cuda"` 需 `ENABLE_CUDA` 构建 | 改成 `"cuda"` 后结果不再与黄金值逐位可比（§3） |

新增参数时，`config.h` 默认值、`config.cpp` 的 `get(...)`、`configs/default.json` 三处要同时改，
并在 05 里写明依据。配置解析会拒绝非法的 `lambda_schedule` 和非有限、非正的尺度。

### 6.4 编码约定（摘自 05 铁律，与回归直接相关的几条）

- **可复现（铁律 7）**：禁止 `omp reduction(+:)`，标量求和走 `numeric/reduction.h` 的 `deterministicSum`；
  所有分桶并行按**固定桶数**而不是线程数；随机数只用 `Config::random_seed` 驱动的 `std::mt19937`；
  从无序容器取出的候选要**排序后**再累加。
- **优化器只认 `obj_and_grad_fn`（铁律 6）**：不要让 `nesterov.cpp` 知道宏、filler 或 τ。
- **保存"最优解"时，保存测出这个最优值的那个点**：带前瞻的优化器里 u 和 v 不是同一个东西（G3、G4）。
- **任何没有单调保证的迭代过程都必须单独记住最优解**，不能交付"最后一次迭代的解"（G2、U4）。
- **修复类算法每一步都只接受目标下降**（分离、推挤、网格搜索、最终回拉都是如此），否则多轮之后会振荡。
- **诊断代码与算法代码分开构建**（`ENABLE_M3_PAIR` 等选项），生产 CLI 的二进制在加入诊断工具前后应保持不变，
  避免把额外的诊断指标误判为算法行为变化。

## 7. 每次改动后的验证流程

### 7.1 每次提交前（几分钟）

```bash
cmake --build build -j16 && cmake --build build_clean -j16
OMP_NUM_THREADS=1  ctest --test-dir build -LE golden
OMP_NUM_THREADS=8  ctest --test-dir build -LE golden
OMP_NUM_THREADS=32 ctest --test-dir build -LE golden
ctest --test-dir build -L m3 --output-on-failure   # 当前口径黄金 + 跨线程一致性，9 个用例，串行
```

非黄金组全部通过才算通过。改到优化器、停滞保护、mLG 时，额外看一眼这几个单测的输出：
`test_nesterov`、`test_eplace`、`test_macro_sa`、`test_repair_candidates`、`test_lambda_schedule`。
`test/test_m3_audit.py` 守的是闸门脚本本身（缺种子拒绝、同权汇总、超 3% 拒绝等）。

**黄金用例失败时**：先确认是不是在生成黄金值的同一环境（§4.7）。不同环境下的失败不能直接说明代码有回归，
要先在本环境跑一遍改动前的基线再比较。同一环境下，若只有部分线程数失败，那是铁律 7 的回归，不要更新黄金值；
若是有意改变结果，用 `scripts/m3_golden.py --bin <CLI> --update` 重新生成（1/8/32 线程不一致时它拒绝写入），
并做 §7.2 的全量回归。历史口径的黄金值需配置 `-DENABLE_LEGACY_GOLDEN=ON` 后用 `ctest -L legacy` 显式运行。

改到 `src/numeric/` 或 CUDA 相关代码时，另跑一遍 CUDA 构建（需要 GPU）：

```bash
cmake -B build_cuda -DENABLE_CUDA=ON && cmake --build build_cuda -j16
ctest --test-dir build_cuda -LE golden   # 多出 test_poisson_parity，test_poisson 会对 CUDA 再跑一遍
```

### 7.2 改到 QP、mGP、mLG、cGP 任何一处时：全量回归

```bash
# 1. 基线与候选各跑一遍（默认种子，32 个设计；本机需显式指定 benchmark 根目录）
python3 scripts/m3_audit.py --bin <基线构建>/superplace-cli --out results/m3/<基线> --bench-root benchmarks
python3 scripts/m3_audit.py --bin <候选构建>/superplace-cli --out results/m3/<候选> --bench-root benchmarks

# 2. 只改了 mLG 及之后的阶段时，用配对工具补齐 19 个含宏设计的固定种子 1、2、3、4
cmake -S . -B build/m3-pair -DENABLE_M3_PAIR=ON -DM3_REFERENCE_COMMIT=<基线提交>
cmake --build build/m3-pair --target superplace-m3-pair -j16
python3 scripts/m3_pair_audit.py --bin build/m3-pair/superplace-m3-pair \
    --baseline results/m3/<基线> --candidate results/m3/<候选>

# 3. 闸门（有任何失败即返回非零）
python3 scripts/m3_compare.py results/m3/<基线> results/m3/<候选> --overlap
```

改到 mGP 或更早的阶段时，配对工具不适用（它共享 mGP），要用 `m3_audit.py --seeds 1 2 3 4`
直接补跑 19 个含宏设计。闸门通过只表示没有新增回归，§4 的既有问题不会因此消失。

### 7.3 跨线程数一致性

由 `ctest -L m3` 覆盖：thin1、adaptec1、MMS adaptec1 各在 1/8/32 线程下运行，输出必须等于同一份黄金值。

黄金集没有覆盖回溯较多（MMS newblue1）和触发停滞（MMS bigblue2）的设计。改到回溯或停滞保护时，建议手工补测：

```bash
for t in 1 8 32; do
  OMP_NUM_THREADS=$t ./build_clean/superplace-cli --aux benchmarks/mms/bigblue2/bigblue2.aux \
      --stage init,gp --config configs/default.json --no-plot --out results/thr_$t
done
cmp results/thr_1/bigblue2/bigblue2.gp.pl results/thr_8/bigblue2/bigblue2.gp.pl
cmp results/thr_1/bigblue2/bigblue2.gp.pl results/thr_32/bigblue2/bigblue2.gp.pl
```

### 7.4 环境注意事项

- **线程数用 16，不要用满 32。** WSL 在持续满载下会自动重启（M3 期间发生过四次），
  后台任务和 `/tmp` 里的东西都会丢。32 线程的黄金用例时间短，可以保留。
- 日志和中间结果写到 `results/` 下，不要写 `/tmp`。`m3_audit.py` 与 `run_audit.sh` 都可续跑。
- 计时比较只在同一会话里背靠背进行（U9）；`m3_pair_audit` 的 `wall_s` 不是独立的性能数据。

for r in 1 2; do

   在本机和同伴机器上都用 `-DENABLE_NATIVE=OFF` 构建同一提交，比较 thin1 的 `init.pl`；
   若一致，说明来源是 `-march=native`，可以把黄金测试改为用非 native 构建、做成跨机器可用；
   若仍不一致，再逐项比较编译器、Eigen、FFTW 版本。在查清之前，每台机器各自维护一份黄金值，并在 PR 里注明环境。
   顺带复核 §4.3 的 ISPD bigblue3 是否只是同一来源。
3. **分析 mGP 稳定性问题**：ISPD newblue4（§4.2，最终交付未达标）、ISPD bigblue3（§4.3）、MMS newblue6（§4.5）。
   按 05 §5.5.9 的三种类型（步长尖峰、真实平台、轮数不够）先给每个设计分类：看 `metrics.csv` 中的步长、λ、
   `eval_lambda`、`evaluations` 的变化，再决定是否要改算法。
4. **λ 参考尺度**（§4.6）：先分析 relative 模式为什么让线长变差（λ 的增长速度与 HPWL 的关系），
   再考虑只在初期放大参考量、或给 λ 增速设上限等折中做法。验收必须用五种子配对口径，不能只看迭代次数。
5. **让当前口径的验收数据对团队可复核**（§4.10）：把 `m3_audit.py` 的默认 `--bench-root` 改为仓库内的 `benchmarks/`；
   把 `final-metrics.json`、`final-gate.txt` 这类小体积的汇总结果纳入版本管理或共享位置，原始运行目录保留在本机。
   统一新旧两套审计工具，旧工具只保留用于历史对比；`m3_audit.py` 目前强制 `poisson_backend=cpu`，
   需要加一个选项支持 GPU 子集回归。
6. **工程化措施**（§9）：P1-1 不变量硬检查、P2-1 持续集成与分支保护、P3-2 把工作量计数纳入闸门、P3-3 Sanitizer 构建。
   持续集成依赖第 2 项：黄金值必须先做到跨机器可用。
7. **SA 的长期方向"先合法、再精修"**（§4.8，05 §5.6.2 有分析）。

### P1-1 不变量写成代码里的硬检查

现在这些性质要么只打印一行，要么只打 ERROR，**程序照样以 0 退出**（`main.cpp` 只在异常时返回非零）。
11-10 的闸门在脚本层面补上了大部分检查，但单次运行、持续集成和其他调用方仍察觉不到。

| 不变量 | 现在的行为 | 应改为 |
| --- | --- | --- |
| mLG 结束后宏重叠为 0 | 只打印"重叠 X -> Y" | Y > 0 时报错，进程以非零退出 |
| 空间索引自检一致（L6） | `SP_ERROR` 后继续 | 中止 |
| cGP 期间冻结的宏不动（L11） | `SP_ERROR` 后继续 | 以非零退出 |
| 停滞回退后重算的 τ 等于声称值（G3） | 无检查 | 不等时报错 |
| 判定达标后交付点的 τ 低于阈值（G4） | 无检查 | 不满足时报错 |
| 无出界、无 NaN/Inf（X1、X2） | NaN 时中止当前阶段，出界只记录 | 以非零退出 |

建议统一一个"致命错误"出口：记录日志、写入 `summary.json`、最后返回非零。
